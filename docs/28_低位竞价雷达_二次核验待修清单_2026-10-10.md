## P0：先修阻断项

### [ ] R-01 预览快照写入立即报 `ImportError`

- **证据**：`backend/plugins/auction_radar/service.py:222-230` 从 `backend.plugins.common` 导入 `atomic_write_json`，但该函数实际定义在 `backend/services/snapshot_store.py:82`。`run_auction_poll_once()` 每轮都会调用 `write_preliminary()`。
- **已复现**：独立调用 `write_preliminary([], 北京时间 datetime)` 返回 `ImportError: cannot import name 'atomic_write_json' from 'backend.plugins.common'`。因此当前 daemon 不能完成一轮正常采集；23 项测试没有直接执行这个真实写入入口。
- **建议修复**：改用实际模块的原子写函数，明确写入失败时本轮的状态与日志；不要在测试中 mock 掉此函数。
- **关闭标准**：真实调用 `run_auction_poll_once()`（仅 mock 行情源，快照写入指向临时目录）成功生成可读取的 `PRELIMINARY` 文件；重复写入、异常中断后文件仍是完整 JSON。

### [ ] R-02 最终行情未参与最终全池重排

- **证据**：`backend/plugins/auction_radar/service.py:381-389` 每次重拉行情后只生成 `evidence`，随后 `score_pool(frozen, store, now)` 仍读取竞价阶段的旧内存帧；最终拉取的报价没有进入帧或重算因子。`scope_complete` 的 `min(len(frozen.items), pool_max)` 还可能把未覆盖的全池误判为完整。`service.py:398-405` 的部分确认分支未检查完整范围。
- **影响**：09:25 后某票因最终价量变化跳入 TopN 时，旧榜可能仍被发布；部分确认也可能对不完整范围的名单发布观察清单。
- **建议修复**：逐票校验并纳入最终报价，基于最终证据重算全冻结池候选、排序和 TopN；完整范围须以冻结池实际名单及逐票结果判断，缺失票显式记录，不以 `pool_max` 代替覆盖。部分确认仅在方案允许的完整重排范围内发布，保留原观察位次及缺失原因。
- **关闭标准**：新增测试让预测排名第 N+1 的股票在最终报价后升至 TopN，发布结果必须包含它；再测全池缺票时不得发布 `CONFIRMED` 或 `PARTIAL_CONFIRMED` 的完整范围榜单。

### [ ] R-03 Outbox 有 dispatcher，但运行链没有调用

- **证据**：`backend/plugins/auction_radar/outbox.py:88` 定义 `dispatch_outbox()`；当前业务代码和调度脚本没有调用它。`service.py:284-314` 还先将通知入队为 `READY`，后发布快照；候选写入与入队返回值未检查。
- **影响**：打开 Outbox 后任务可能长期停在 `READY`，不会自动发邮件；若将来直接启动 dispatcher，可能出现邮件早于快照发布，或部分写入失败仍继续发布。
- **建议修复**：在单进程调度中明确启动 dispatcher，定时消费 READY/到期重试任务；设计并测试“DB 候选与待发布事件持久化 → 原子快照可见 → READY 可发送”的可恢复顺序。逐步检查数据库写入结果，失败不得假报 `PUBLISHED`。
- **关闭标准**：用假的 SMTP 适配器做非 mock 状态库的集成测试，验证 READY→SENDING→ACCEPTED、失败重试、崩溃恢复及“快照不可读时不发送”；启动 daemon 后无需手动调用函数即可消费任务。

### [ ] R-04 调度跨越 09:25 的时刻判断不准确

- **证据**：`backend/plugins/auction_radar/scheduler.py:36-55` 把时间截成 `%H:%M`，且采集条件包含 `"09:25"`，所以 **09:25:00–09:25:59** 仍走采集，通常到 09:26 才进入最终确认；`finalized=True` 在确认成功前即设置，异常后不会重试。
- **建议修复**：用带北京时间时区的完整 `datetime` 边界：`09:15:00 <= now < 09:25:00` 才是竞价采集；09:25 后进入最终确认。只有拿到可恢复的终态后才设本地 finalized 标记，重启/失败路径以 DB 状态判定。
- **关闭标准**：时间冻结测试覆盖 09:24:59、09:25:00、09:25:59、09:26:00 及确认过程抛异常后的重试，不把 09:25 后旧预测帧当最终结果。

### [ ] R-05 `dry_run` 仍占用正式唯一 run

- **证据**：`backend/plugins/auction_radar/service.py:349-373` 在判断 `dry_run` 前执行 `claim_run_once()` 与 `update_run_checked()`；`publish_final()` 仅跳过后续发布写入。一次演练可先占用 `(trade_date, strategy_version, revision=1)`，正式运行再进入 `not claimed → read_latest()`。
- **建议修复**：演练使用完全隔离的临时库/策略版本，或在 `dry_run` 路径不抢占、更新生产 run，不建生产 Outbox。CLI 与 API 默认值也要一致明确。
- **关闭标准**：同日先 dry-run 再正式确认，正式流程仍能抢占并发布；dry-run 前后生产 `auction_runs/auction_candidates/auction_outbox` 行数与状态不变。

## P1：工程验收与安全项

### [ ] R-06 M0–M5 六里程碑尚未形成每日闭环

- **证据**：当前只有 `service.py:373,393-405` 写 M3/M4 的内存状态，M4 又是在 `publish_final()` 将旧 `milestones_json` 写入 DB **之后**才置为 done；M0/M1/M2/M5 没有完整的同日持久化接线。`market_sampler.sample_market_once()` 与 `outcomes.append_outcome_labels()` 也未接入日常调度。
- **建议修复**：明确 T−1 M0、T 日 M1–M4、盘后 M5 的目标交易日关联、各阶段持久化时机及失败/跳过终态；M4 以 SMTP 受理结果为通知证据，不以快照 `PUBLISHED` 代替。
- **关闭标准**：用正常、空池、源失败、SMTP 失败四种回放分别生成可查询的六阶段报告；每阶段状态、开始/结束时间、证据或跳过原因与实际一致，不补造时间戳。

### [ ] R-07 盘后产池脚本没有让业务失败真正失败

- **证据**：`scripts/run_daily.sh:20-23` 的快照检查只打印 `OK/FAIL`，没有按 `ok` 设置非零退出码；超 15:50 只打印日志。`backend/main.py:477-486` 的插件 CLI 异常也只记录、不向 shell 返回失败。脚本把产池放在智能选股任务之后，仍可能错过截止。
- **建议修复**：业务快照校验、CLI 业务状态和完成 deadline 都应形成可机器判断的失败/告警；产池放在主筛选完成后、其它可延后任务之前。不要只凭 `set -eo pipefail` 判断业务成功。
- **关闭标准**：模拟快照缺失、`status != completed`、日期错误、插件异常、15:50 超时，调度记录均不能显示产池成功；次晨门禁不能使用旧池。

### [ ] R-08 trigger 启用后仍未验证请求方 token

- **证据**：`backend/plugins/auction_radar/router.py:70-79` 只检查配置中 `trigger_token` 非空，没有读取并比对请求头或其它请求凭据。默认关闭时风险受限，但一旦启用，任何能访问接口的请求都可能触发流程。
- **建议修复**：保持默认关闭；启用时必须校验请求凭据（常量时间比较），缺失/错误返回 401/403，并限制可触发动作及频率。
- **关闭标准**：测试关闭、服务端空 token、请求不带 token、错误 token、正确 token 五种情况；前四种均不能进入 `run_auction_radar_once()`。
