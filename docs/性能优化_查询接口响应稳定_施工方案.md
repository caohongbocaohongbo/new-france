# 性能优化 · 查询接口响应稳定 — 施工级技术方案 v2

> 状态：施工方案（待开工）。  
> 范围：查询/读取链路、快照可靠性、响应体积与 SQLite 并发稳定。  
> 约束：不改业务阈值和策略公式；不引入 Redis/外部数据库；每个批次可独立验收和回滚。  
> 核心结论：本轮先优化“快照版本化 + 早期 304 + 大响应裁剪 + 远程快照合并缓存”，不把重复索引、全量接口线程化、K 线预热当作首批优化。

## 1. 目标与非目标

### 1.1 目标

1. 降低 `*_latest` / `history` / `snapshot` / `perf` 等读接口的暖态 P95 和传输体积。
2. 304 请求在 JSON 解析、字段裁剪和重序列化之前返回，不再“完整生成响应后才算 MD5”。
3. 消除目标快照文件的半写 JSON 风险，并统一本地/远程快照的读取语义。
4. 防止同一远程快照在并发或连续请求中反复下载，同时保留可用的陈旧快照。
5. 将 SQLite 锁冲突从“立即失败”降为“可观测、有界等待、短事务重试”，不承诺 WAL 可消除所有写写冲突。
6. 将 Render 平台唤醒、应用启动、业务处理和响应传输分开测量，避免用单一 `dur_ms` 得出错误结论。

### 1.2 非目标

- 不改变任何选股阈值、因子权重、信号判定或邮件规则。
- 不迁移主数据库，不引入 Redis、对象存储或消息队列。
- 不在本轮重写前端框架。
- 不为了“看起来有优化”而新建已有等价索引。
- 不把 Render 平台级冷唤醒时间误归因为 Python import 时间。

## 2. 已核验现状与优先级

### 2.1 本地样本基线

2026-09-21 使用 FastAPI `TestClient` 对当前本地快照连续请求 5 次。下表用于施工排序，不代替 Render 生产 P95：

| 接口 | 当前响应体 | 暖态耗时约 | 条件请求约 | 判断 |
|---|---:|---:|---:|---|
| `/api/v1/principal-capital/tier-flow/latest` | 873 KB | 64 ms | 304 为 64 ms | 最高优先级 |
| `/api/v1/overnight-arbitrage/history` | 353 KB | 27 ms | 304 为 27 ms | 高优先级 |
| `/api/v1/screening/latest` | 178 KB | 23 ms | 304 为 23 ms | 高优先级 |
| `/api/v1/overnight-arbitrage/latest` | 294 KB | 20 ms | 304 为 20 ms | 高优先级 |
| `/api/v1/smart-picker/latest` | 31 KB | 4 ms | 304 为 3 ms | 暂不裁剪 |

补充事实：

- `tier_flow_latest.json` 约 1.2 MB、3049 条；前端只渲染前 100 条，且只使用 6 个字段。
- `overnight_arbitrage_latest.json` 约 464 KB；当前样本中仅 `data_quality.removed` 约占 289 KB。
- `overnight_arbitrage_history.json` 约 564 KB、512 个按股票聚合的记录。
- `smart_picker_latest.json` 约 53 KB，接口已服务端过滤、排序、分页，不是本轮瓶颈。
- 当前 ETag 中间件会完整消费响应体、拼接 bytes、计算 MD5 后才判断 304，所以 304 几乎不节省服务端 CPU。
- `smart_picker_hits(date)`、`smart_picker_hits(code, date)`、`picker_perf_daily(signal_date)`、`picker_perf_daily(code, signal_date)` 索引已经存在；当前两张表仅数百行。
- 本地 `import backend.main` + `get_app()` 约 0.75s；生产 30–60s 首请求应与 Render 平台唤醒分开测量。

### 2.2 性能目标

以 P0 生产基线为最终对照，本地数据仅用于施工优先级。

| 指标 | 目标 |
|---|---|
| 目标大接口暖态 P95 | 相对基线降低至少 40% |
| 已命中 ETag 的本地 304 | P95 ≤ 5ms，且不进行 JSON 解析/序列化 |
| `tier-flow/latest` 列表响应 | 默认不超过 100 条，原始 JSON 体积下降 ≥ 80% |
| `overnight/latest` 列表响应 | 默认不含 `data_quality.removed`，原始 JSON 体积下降 ≥ 70% |
| history 响应 | 有默认页大小和硬上限，默认不携带嵌套长明细 |
| 远程快照 | 同 key 并发只产生 1 次上游请求；上游失败时可返回陈旧可用数据 |
| SQLite | 并发压测不出现未处理的 `database is locked`；所有锁等待可观测 |
| 功能契约 | 前端页面、轮询状态和详情字段无回归 |

## 3. 目标架构

### 3.1 统一快照存储层

新增 `backend/services/snapshot_store.py`（若后续确认 `backend/utils/io_util.py` 更合适，可改用该路径，但不能同时保留多套重复实现），统一提供：

- `atomic_write_json(path, payload) -> SnapshotMeta`
- `read_snapshot_entry(path) -> SnapshotEntry | None`
- `json_response_from_entry(request, entry, cache_control=...) -> Response`
- `fetch_remote_snapshot(key, url, policy) -> SnapshotEntry | None`

`SnapshotEntry` 至少包含：

- 预序列化的 UTF-8 JSON bytes。
- 必要时才创建的解析对象。
- 基于内容生成的弱 ETag，如 `W/"<sha256>"`。
- `mtime_ns + size + inode`（平台不支持 inode 时退化为前两项）。
- `loaded_at / source / stale / upstream_etag / upstream_last_modified`。

实现约束：

1. 序列化函数内部完整实现 NaN/Infinity 清理，不引用未定义的 `_json_safe`。
2. 临时文件名含 PID + UUID，避免多写者冲突。
3. 写入临时文件后 `flush + fsync`，再 `os.replace`；目录 `fsync` 作 best-effort。
4. 不对缓存中共享 dict 做原地修改；裁剪/补字段必须构造新对象。
5. 内存缓存使用 LRU + 总字节上限，默认不超过 32 MB，而不是只按文件数限制。
6. 未变更的无过滤响应直接返回 bytes，避免每次 `json.loads -> dict -> json.dumps`。

### 3.2 早期条件请求

当接口直接对应一份快照时：

1. 获取缓存中的 `SnapshotEntry` 元数据。
2. 在 JSON 解析、过滤和序列化前比较 `If-None-Match`。
3. 命中时返回 304，并保留 `ETag` / `Cache-Control` / `Vary`。
4. 未命中时直接返回预序列化 bytes。

不再使用当前“拦截所有 JSON 响应并重新缓冲”的全局 ETag 中间件。动态过滤类接口如需 ETag，由“底层快照版本 + 规范化查询参数”生成，不对响应体重复哈希。

### 3.3 远程快照策略

远程 `data-snapshots` 是 Render Web 和 Cron 分离部署下的共享数据桥梁，不应被视为偶发异常分支。

默认策略：

- latest/report：成功 TTL 300s。
- history：成功 TTL 600s。
- source health：成功 TTL 60s。
- 超时：连接 1.5s，总时间 3s；有 stale 数据时不等待同步刷新。
- 失败退避：3s → 10s → 30s → 60s，附加小幅随机抖动。
- 支持上游 `ETag` / `Last-Modified`，条件 GET 命中时延长本地 TTL。
- 同 key 使用 single-flight，同时只有一个上游请求。
- stale-while-revalidate：有陈旧但可解析的快照时立即返回，在后台尝试刷新。

状态语义不得被缓存破坏：

- 本地 `running` 必须返回给轮询端，不能被远程旧 `completed` 覆盖。
- 本地存在同一任务的完成版本时优先本地。
- 本地 `empty`/缺失时才使用远程完成快照。
- 返回 stale 数据时明确携带 `_source`、`stale`、`fetched_at`和 `refresh_error`。

### 3.4 Cron 产出 API-ready 快照

对体积大、查询形态稳定的数据，优先在产生侧同时输出：

- `*_latest_full.json`：诊断/审计用完整快照。
- `*_latest_compact.json`：前端列表直接消费。
- `snapshot_manifest.json`：记录文件名、版本、生成时间、字节数和 digest。

这样 Web 实例无需在每次请求中读入完整文件再现场裁剪。沿用现有 `data-snapshots` 通道，不增加新外部服务。

## 4. P0 — 完整观测基线

### 4.1 应用内观测

文件：`backend/main.py` + 新增 `backend/middleware/performance.py`。

使用纯 ASGI middleware，通过包装 `send` 记录第一个响应字节和最后一个响应字节，避免 `BaseHTTPMiddleware` 带来额外缓冲或流式响应语义差异。

它必须位于 GZip、ETag 和路由之外，验收测试必须证明日志包含全部响应生成与发送阶段，不只依赖注册顺序的文字描述。

日志字段：

- `request_id`
- `method`
- `route_template`（不直接用高基数原始 path）
- `status`
- `ttfb_ms`
- `duration_ms`
- `response_bytes`
- `content_encoding`
- `etag_result=hit|miss|none`
- `snapshot_source=memory|local|remote|stale|none`
- `snapshot_cache=hit|miss|refresh|singleflight_wait`
- `upstream_ms`
- `process_uptime_s`
- `error_type`

health 请求不写普通 access 日志，但每 5 分钟汇总一次 health 延迟和进程 uptime，用于区分重启与日常请求。

### 4.2 外部冷启动观测

应用内 middleware 无法观测 Render 在进程启动前的排队/唤醒时间。使用现有 UptimeRobot 或等价外部探针，分别记录：

- `/api/v1/system/health` 端到端时间。
- 紧随其后的一个小型读接口时间。
- 进程 uptime/部署版本。

冷启动与暖态 P95 分开报告，不混在同一个延迟数列中。

### 4.3 P0 验收

- 用受控的慢 ETag/GZip 测试证明 `duration_ms` 包含其开销。
- 用流式响应测试证明 `ttfb_ms < duration_ms`，且不缓冲 SSE。
- 产生按 `route_template` 聚合的请求数、P50/P95/P99、失败率、响应字节 TOP10。
- 连续收集至少 1 个完整交易日；若请求量不足，补充可重放的本地基准。

## 5. P1 — 快照稳定基座与早期 304

### 5.1 统一原子写

首批迁移目标必须一次完整盖住“热读取接口对应的所有写入点”，不使用“其余逐步替换”作为本阶段验收。

至少包含：

- `backend/api/router_screening.py`
- `backend/plugins/overnight_arbitrage/service.py`
- `backend/plugins/principal_capital/service.py`
- `backend/plugins/common.py` 的通用快照写入
- `backend/plugins/smart_money_radar/service.py` 及其 orderbook/orderflow/auction 快照
- `backend/services/task_history.py`
- `backend/services/optional_source_health.py`
- 与上述热接口配对的历史文件写入点

对非 JSON 配置/监控列表的写入不强行纳入本批。

### 5.2 统一读取缓存

- 无过滤接口优先使用 bytes 缓存直接响应。
- 有过滤/排序的接口使用受保护的 parsed 缓存，不允许调用方原地修改。
- 文件替换后通过 stat signature 失效；应用内写入同时主动更新对应 entry。
- 缓存统计暴露 hit/miss/eviction/bytes，不在每次请求写高频 INFO 日志。

### 5.3 替换全局 ETag 中间件

迁移顺序：

1. 先为目标快照接口接入早期 ETag。
2. 验证前端 `window.__etagCache` 对弱 ETag 和 304 回放正常。
3. 再删除 `backend/main.py` 现有全局 `_ETagMiddleware`。
4. 对尚未迁移的小型动态接口暂不发 ETag，不保留昂贵的全局兜底。

### 5.4 同步阻塞链路处理

不做“全部 `async def` 改 `def`”的机械替换，按以下规则处理：

- 可能执行本地文件读、SQLite、pandas 或同步 HTTP 的端点：改为普通 `def`，或用 `asyncio.to_thread` 包住明确阻塞段。
- 纯内存、已命中快照的小接口保持 `async def`，避免无意义的线程池调度。
- 远程请求必须有超时和 single-flight，不得在事件循环中直接调用 `requests.get`。

### 5.5 P1 验收

- 注入“临时文件写入后、replace 前失败”，旧正式文件仍可读。
- 并发写相同文件时临时文件不重名，正式文件永远是完整 JSON。
- 文件内容不变时连续请求只解析一次。
- 304 命中时不执行 `json.loads`、字段过滤、FastAPI JSON 序列化或响应体哈希。
- 并发 20 个相同远程 key 的请求只产生 1 次上游请求。
- 远程失败时 stale 快照可用，且不会每 3 秒永久重试。
- 本地 `running` 状态不被远程旧 `completed` 掩盖。

## 6. P2 — 按实际瓶颈做接口瘦身

### 6.1 契约迁移规则

所有瘦身改动都使用兼容迁移：

1. 新增 `view=compact|full` 或新增独立 compact endpoint。
2. 先修改前端显式请求 compact，同时保留旧 full 语义。
3. 增加前后端契约测试后再评估是否将 compact 设为默认。
4. 不在同一次部署中无过渡地删除旧字段。

### 6.2 第一优先级：tier-flow/latest

文件：

- `backend/plugins/principal_capital/router.py`
- `backend/plugins/principal_capital/tier_flow.py`
- `frontend/js/plugins/research_plugins.js`

compact 响应规则：

- `limit` 默认 100，硬上限 200。
- 返回 `total / returned / limit / offset / status / now / active_source / degraded / states`。
- item 默认字段：`code / name / super_net / big_net / smart_ratio / state`。
- 排序和分页在服务端完成；前端不再接收 3049 条后执行 `slice(0, 100)`。
- 若前端需要更多字段，通过白名单 `fields` 扩展，不接受任意列名。

### 6.3 第二优先级：overnight-arbitrage/latest

compact 响应保留：

- 顶层：`status / strategy / date / generated_at / valid_window / buy_count / watch_count / total_candidates / total_scanned / source_status / empty_reason / trade_note`。
- result：`code / name / action / decision_score / current_price / change_pct / turnover / volume_ratio / reasons / risks`。

compact 默认不返回：

- `data_quality.removed`
- 全量 `rejected`
- 逐票原始行情/中间因子

诊断数据放入 `/diagnostics/latest` 或 `view=full`，并保留鉴权和体积上限。不得使用 `price / score / strategy` 等与现有前端不匹配的替代字段名。

### 6.4 第三优先级：overnight-arbitrage/history

- `limit` 默认 100，硬上限 200；支持 `offset / code / date_from / date_to`。
- 列表默认只返回每只股的汇总字段，不返回嵌套 `recommendations`。
- 新增 `/{code}/history` 返回单股推荐明细。
- 在 `update_overnight_history` 写入时同步生成 compact summary artifact；请求时不先解析 500KB 完整文件再分页。

### 6.5 第四优先级：screening/latest

先用前端字段契约测试确认列表、详情和报告导出的依赖，再执行：

- `view=summary`：列表所需字段。
- `/{code}` 或现有详情接口：`price_history / audit / evidence / factors`等长字段。
- `report_md / report_html` 不在默认列表请求中回传，改由报告接口按需获取。

### 6.6 暂不优化：smart-picker/latest

当前该接口已有服务端过滤/排序/分页，响应体和耗时均较小。本轮只增加契约回归测试，不删减 `hit_flags / pct / hits / badges`。只有 P0 生产数据证明它进入 TOP 瓶颈后才重新排期。

### 6.7 GZip

在字段裁剪完成后启用：

```python
from fastapi.middleware.gzip import GZipMiddleware

app.add_middleware(GZipMiddleware, minimum_size=1024, compresslevel=5)
```

验收时比较原始体积、压缩体积和 CPU 耗时；若当前 Starlette 版本不支持 `compresslevel`，固定兼容版本或使用默认参数后实测，不盲目追求最高压缩级别。

ETag 使用弱验证器，响应包含 `Vary: Accept-Encoding`，并测试 gzip/非 gzip 客户端都能正确进行条件请求。

## 7. P3 — SQLite 稳定性（证据驱动）

### 7.1 连接配置

文件：`backend/db/database.py`。

```python
engine = create_engine(
    DATABASE_URL,
    echo=False,
    connect_args={"check_same_thread": False, "timeout": 5},
)
```

连接级 PRAGMA：

- `PRAGMA busy_timeout=5000`
- `PRAGMA synchronous=NORMAL`（确认 WAL 已开启后）
- 如现有数据模型依赖外键，同时显式开启 `PRAGMA foreign_keys=ON`。

`journal_mode=WAL` 在 `init_db()` 中受控初始化并校验结果，不依赖每个新连接都重复切换 journal mode。

默认不启用 `pool_pre_ping`：SQLite 本地文件连接不需要用它解决远程 TCP 断连，而每次 checkout 额外探测可能增加开销。只在有可复现的失效连接证据时启用。

### 7.2 事务与重试

- 写事务只包含必要 SQL，网络请求、pandas 计算和 JSON 序列化不得放在事务内。
- 对幂等写操作可对 `SQLITE_BUSY` 做有界重试，不重试未知数据库异常。
- 记录 `lock_wait_ms / retry_count / operation / table`，避免用“没报错”掩盖 5 秒长尾等待。

### 7.3 索引决策

本轮不新增以下重复索引：

- `picker_perf_daily(signal_date, code)`
- `smart_picker_hits(date)`
- `smart_picker_hits(code, date)`

只有同时满足以下条件时才补索引：

1. P0 显示对应 SQLite 查询进入慢查询 TOP。
2. `EXPLAIN QUERY PLAN` 显示全表扫描且表规模已足以影响 P95。
3. 现有索引不能覆盖该 WHERE/ORDER BY。
4. 补索引前后有可重复基准对比。

### 7.4 P3 验收与回滚

- 并发压测：20 个读者 + 2 个写者，每个写者至少 100 次短事务。
- 无未处理 `database is locked`，并输出锁等待分布。
- 逐连接验证 `busy_timeout`；启动后验证 `journal_mode=wal`。
- WAL 回滚不是“删除代码”：需先 checkpoint，再在无并发写入时显式执行 `PRAGMA journal_mode=DELETE`，并确认 `-wal/-shm` 处理完成。

## 8. P4 — K 线持久化读穿（独立实验批次）

本阶段不与普通 JSON 读接口优化同批施工。当图表/K 线接口进入生产慢请求 TOP 后再开工。

目标读穿次序：

1. 进程内 K 线缓存。
2. `bars_store` 查询已有覆盖，校验 `adjustment / adjustment_version / is_final / 日期范围`。
3. 只向远程数据源请求缺失范围。
4. 合并、去重、校验后幂等 upsert。
5. 当日未收盘 K 线使用短 TTL；已完成历史条不重复拉取。

不把 Render Cron 中的进程内预热当作 Web 优化：Cron 与 Web 是不同实例，不共享内存和临时 SQLite。如需跨实例加速，Cron 应生成版本化图表快照并经现有 `data-snapshots` 通道供 Web 读取。

## 9. P5 — 冷启动（独立优化）

只在 P0 拿到“平台唤醒”与“应用 import/app 初始化”的分段数据后实施。

1. 使用 import profile 找出实际 TOP 重依赖，不仅凭感觉延迟 pandas/akshare/pytdx。
2. 将只在 POST 任务、CLI 或图表生成中需要的重模块移到具体函数内导入。
3. 确保 health 不触发远程网络、大 JSON 预热或数据库全表扫描。
4. 只在服务已 ready 后启动有限、可取消的后台预热；预热不得与首个用户请求抢占全部线程池或上游连接。
5. 在 `render.yaml` 配置明确的 health check path（以当前 Render Blueprint 支持的字段为准）。

如应用启动仅占冷启动总时间的小部分，则不继续做大规模延迟导入重构，避免增加首次功能请求的不确定性。

## 10. 施工批次与依赖

```text
批次 A：P0 完整观测
   └── 产出生产基线与瓶颈排名

批次 B：P1 快照存储层 + 远程合并缓存 + 早期 304
   └── 删除现有全局响应体 ETag 缓冲

批次 C：P2 tier-flow + overnight + screening 契约化瘦身
   └── 前端显式切 compact，再启用 GZip

批次 D：P3 SQLite WAL/事务稳定
   └── 仅当观测证明必要时补新索引

批次 E：P4 K 线读穿 / P5 冷启动
   └── 两者独立立项、独立回滚
```

不把 P0+P1+P2 合在一个 PR；否则基线、根因和改善量无法分离。

## 11. 测试计划

### 11.1 单元测试

- 原子写：序列化失败、写入失败、replace 前失败、并发写、临时文件清理。
- 缓存：stat 命中/失效、LRU 逐出、字节上限、返回对象不被调用方污染。
- ETag：命中 304、未命中 200、弱 ETag、gzip/非 gzip、304 保留必要响应头。
- 远程快照：正缓存、负退避、single-flight、条件 GET、stale-while-revalidate。
- 状态优先级：本地 `running` 不被远程 `completed` 覆盖。
- SQLite：每个连接的 PRAGMA、WAL 初始化、幂等 busy 重试。

### 11.2 契约与集成测试

- 从前端渲染器建立字段契约，确认 compact 不缺字段。
- `tier-flow` 默认返回数不超过 100，硬上限不可绕过。
- overnight compact 保留 `current_price / decision_score / action / reasons / risks`。
- history 默认不返回嵌套 recommendations，单股详情可完整获取。
- 200/304 前端回放行为一致，切换页面时不重复渲染错误数据。
- 上游超时期间其他小型内存接口仍可响应，证明事件循环未被阻塞。

### 11.3 性能与并发测试

每个目标接口至少测量：

- 冷进程首次请求。
- 本地文件缓存命中。
- 远程快照首次拉取。
- 远程快照 stale 命中。
- ETag 304。
- identity 与 gzip。
- 并发 1/10/50 请求。

输出 P50/P95/P99、TTFB、总耗时、原始字节、传输字节、CPU 时间、峰值 RSS、上游请求数。

## 12. 验收与回滚总表

| 批次 | 主验收 | 回滚方式 |
|---|---|---|
| A 观测 | 完整 TTFB/总耗时/字节/缓存来源可聚合 | 移除 performance middleware，不影响业务 |
| B 快照基座 | 无半写；304 早返回；远程 single-flight/stale 生效 | 保留旧读取适配器一个版本；切回旧路径，不回滚新格式数据 |
| C 接口瘦身 | 目标体积降幅达标；前端/契约全绿 | 前端切回 `view=full`；保留 full endpoint |
| C GZip | 传输字节显著下降，CPU/P95 不恶化 | 移除 GZipMiddleware |
| D SQLite | WAL/busy timeout 生效；锁等待可观测 | checkpoint 后显式恢复 `journal_mode=DELETE`，再回滚代码 |
| E K 线 | 持久化命中率提升，无复权/新鲜度回归 | 关闭 read-through 特性开关，保留旧网络取数路径 |
| E 冷启动 | 应用启动分段耗时下降且首次功能请求无恶化 | 恢复原 import/预热路径 |

## 13. 明确不采用的做法

- 不继续使用“完整生成 JSON 响应后再算 MD5”的全局 ETag。
- 不使用未消费 `ttl` 参数、返回可被污染共享 dict、只按条目数不按字节限制的读缓存。
- 不新增与已有 `idx_sp_* / idx_ppd_*` 等价的重复索引。
- 不把所有纯内存 `async def` 端点统一改为 `def`。
- 不使用 10s 成功 TTL + 3s 固定负缓存持续轰炸按日/按任务更新的远程快照。
- 不把 Cron 进程的 K 线内存预热视为 Web 实例的预热。
- 不在没有前端字段契约测试时改变默认响应字段。
- 不用“删除 WAL 代码”代替完整的 SQLite journal mode 回滚流程。
