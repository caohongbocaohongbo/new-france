# 23 主力资金扫描重构 v2 — 代码核验与修复清单

> 核验日期：2026-09-15（Asia/Shanghai）  
> 核验角色：技术总监  
> 核验对象：DeepSeek 已完成但尚未提交的 23 v2 实现  
> 最终结论：**暂不通过，禁止把 `bulk_admitted` 切为 `true`，M1–M4“代码完成”结论撤回。**

## 1. 结论摘要

本次实现已经建立 v2 的基本骨架，包括执行模式、批次标识、日内状态、候选池、bulk 影子比较、finalizer 和相关单元测试。现有自动化测试全部通过：原实施文档所列回归为 **481/481**，补充覆盖 smart money radar、workflow 与 watchdog 的定向回归为 **122/122**。

但是，全绿测试没有覆盖几条关键生产路径。代码级检查与最小复现确认存在以下阻断问题：

1. strict 真值并非固定的新浪全量同批数据，影子漏检率可能比较不同供应商或不完整样本。
2. 任何非空结果都被写成 `completed`、`coverage_ratio=1.0`、`deadline_met=true`，会制造“完整覆盖”的假象。
3. 配置允许进入 `hybrid`，运行时却仍执行 strict 旧链路，同时报告称自己是 hybrid。
4. 补集审计在约 3200 个代码时通常只抽到 1 个，游标也没有推进，无法覆盖设定的 300 个补集样本。
5. finalizer 会绕过质量门禁与 owner 校验，且结果不明时仍可能重发邮件。
6. API 手工触发会覆盖正式报告，而后台任务默认是 readonly，可能永久留下 `running` 假状态。
7. 新浪必需字段缺失或非法时被转换为 0，缺失数据会变成看似有效的零流入。
8. 新浪批量查询声明的墙钟超时并非真实上限，线程池退出时仍会等待慢请求。

因此，当前实现不能进入 M5 五日影子验收，也不能认定 M1–M4 完成。修复期间生产配置必须保持：

```text
PC_PIPELINE_MODE=strict
PC_BULK_ADMITTED=false
```

并应在代码层拒绝 `hybrid`，避免仅依靠环境变量约束。

## 3. P0 阻断项

### P0-1 strict 真值来源错误，影子漏检比较失真

**位置**

- `backend/plugins/principal_capital/service.py:600-632`
- `backend/plugins/principal_capital/service.py:654-658`
- `backend/plugins/principal_capital/service.py:708`
- `backend/plugins/principal_capital/sources/multi_source.py:228-270`
- `backend/plugins/principal_capital/sources/eastmoney.py:126-137`

**现状**

strict 路径调用 `fetch_market_fund_flow_resilient()`。它优先使用东方财富，其次 akshare，最后才是新浪。`_run_bulk_shadow()` 不检查真值来源，直接把当前 `df` 当作 truth。这样会把供应商口径差异记录成 bulk 漏检，也可能把不完整的东方财富分页结果当完整真值。

影子校验的 universe 又来自 `df` 已返回的代码，而不是预先确定的主板全集。上游漏行时，分母会同步缩小，bulk 校验仍可能显示完整。

**必须修复**

1. 新增明确的 `fetch_strict_truth()`，M5 期间只接受 `sina_full` 同批真值；不允许 cache、Eastmoney 或 AKShare 计入零漏检样本。
2. 在抓取前生成权威主板 universe，记录 `requested_codes`；返回后计算 `received_codes`、`missing_codes` 和覆盖率。
3. 真值不完整时，本轮标记 `partial` 或 `no_data`，`audit.valid_for_admission=false`，不得累积 M5 天数。
4. bulk 与 truth 必须记录同一 `batch_id`、交易日、请求窗口和阈值版本。
5. 东方财富分页改为根据总页数或“最后一页少于页容量”终止，禁止固定 7 页后把非空结果认定完整。

**回归测试**

- Eastmoney 只返回 1 行时，结果不得是 `completed + coverage=1.0`。
- truth 来源不是 `sina_full` 时，`audit.valid_for_admission` 必须为 false。
- universe 3200、收到 3199 时，missing 必须含具体代码且状态不能是 completed。

### P0-2 完成状态、覆盖率和 deadline 被硬编码

**位置**

- `backend/plugins/principal_capital/service.py:708-715`
- `backend/plugins/principal_capital/service.py:786-803`

**证据**

只要数据帧非空，结果固定写入：

```text
status=completed
deadline_met=true
requested_count=len(df)
received_count=len(df)
missing_codes=[]
coverage_ratio=1.0
```

最小复现中，仅返回 1 行也得到 `completed / requested=1 / received=1 / coverage=1.0`。

**必须修复**

1. `requested_count` 从本轮计划 universe 取得，不能从响应行数反推。
2. `received_count` 按有效且唯一的返回代码计算；重复、非法、缺字段行不计入。
3. `missing_codes=requested-received`，状态由覆盖率、质量、超时共同决定。
4. 以 `time.monotonic()` 测量整轮实际耗时，计算 `deadline_met`。
5. `completed` 只允许完整覆盖且质量门禁通过；否则使用 `partial`、`degraded`、`no_data` 或 `strict_fallback`。

### P0-3 hybrid 是“标识生效、执行未生效”

**位置**

- `backend/plugins/principal_capital/config.py:142-150`
- `backend/plugins/principal_capital/service.py:640-827`

**证据**

当 `bulk_admitted=true` 时，模式解析会返回 `hybrid`，但运行函数仍固定调用旧的 resilient 全量扫描，没有执行 coarse union、精算请求或自动回退。最小复现确认报告为 `pipeline_mode=hybrid`，旧链路调用次数仍为 1。

**必须修复**

M6 尚未完成前，先采用安全修复：

```python
if requested_pipeline_mode == "hybrid":
    raise RuntimeError("hybrid 尚未完成生产实现，禁止启用")
```

也可将 `requested_pipeline_mode` 与 `effective_pipeline_mode` 分开记录，但 effective 必须为 strict，状态中必须说明拒绝原因。等 M6 真正实现 coarse → refine → quality gate → auto fallback 后再开放。

### P0-4 补集审计数量错误且不会轮转

**位置**

- `backend/plugins/principal_capital/pipeline.py:141-157`
- `backend/plugins/principal_capital/service.py:622-629`
- `backend/plugins/principal_capital/intraday_state.py:102,122`

**证据**

当前桶数取不小于代码数量的 2 次幂，再只选一个 hash 桶。对 3200 个代码、配置审计 300 个的复现结果为实际仅 1 个；`audit_cursor` 运行后也没有更新，因此下一轮重复同一桶。

**必须修复**

1. 先计算 `complement = universe - coarse_without_audit`，审计只能从补集取样。
2. 按 `SHA-256(code)` 稳定排序后使用环形切片，精确返回 `min(size, len(complement))` 个代码。
3. 函数返回 `(codes, next_cursor)`，official/shadow 对应状态在本轮成功落盘时推进游标。
4. 同一 batch 重放不得推进两次。

**建议实现**

```python
ordered = sorted(complement, key=lambda code: hashlib.sha256(code.encode()).hexdigest())
take = min(size, len(ordered))
start = cursor % len(ordered)
codes = [ordered[(start + i) % len(ordered)] for i in range(take)]
next_cursor = (start + take) % len(ordered)
```

### P0-5 finalizer 绕过质量门禁、owner 与不确定投递状态

**位置**

- `backend/plugins/principal_capital/service.py:830-880`
- `backend/plugins/principal_capital/intraday_state.py:538-551`
- `backend/plugins/principal_capital/intraday_state.py:99-101`

**证据**

`should_finalize_session()` 只检查是否已发送、最新批次是否 completed 以及批次年龄。它没有检查 `latest.quality.notify_eligible`、trade_date、batch/state 一致性和 owner。实测把最新报告设为 `provisional + notify_eligible=false`，finalizer 仍调用邮件发送并返回 sent。

`summary_attempted_at` 会写入，却从不参与下一次决策。如果进程在 SMTP 请求后、`summary_sent` 落盘前退出，下次会再次发送。finalizer 还可以释放并非自己持有的 owner 租约。

**必须修复**

1. finalizer 显式接收 `owner_id`，只允许当前有效 owner 执行和释放自己的租约。
2. 检查报告 `trade_date`、`batch_id` 与 state `last_batch_id` 一致。
3. 仅当 `status=completed` 且 `quality.notify_eligible=true` 时允许发信。
4. 用每 session 投递状态机替代两个布尔字段：`pending`、`sent`、`explicit_failed`、`delivery_unknown`。
5. SMTP 调用前原子落盘 pending/attempt_id；发生超时或进程结果不明时标为 `delivery_unknown`，禁止自动重发，交给人工或带相同幂等键的受控补偿流程。
6. 不应宣称 SMTP “恰好一次”；正确目标是“至多一次自动尝试 + 可审计的不确定状态”。

### P0-6 API 手工触发破坏正式单写者

**位置**

- `backend/plugins/principal_capital/router.py:22-32`
- `backend/plugins/principal_capital/router.py:35-61`

**现状**

`POST /trigger` 在启动任务前无条件把正式 latest 写成 `running`，后台扫描没有传 `execution_mode`，默认 readonly，不会写回最终正式结果。因此一次手工触发就可能让正式 latest 长期停留在 running。后台异常也会覆盖正式报告。

**必须修复**

1. API 手工触发默认执行 `shadow` 或 `readonly`，运行状态写独立的 `principal_capital_manual_status.json`。
2. 禁止 API 路由直接调用 `write_report()`。
3. 若确需 API official，必须使用与 workflow 相同的 owner/lease 协议、显式权限控制与请求限流。
4. 加入集成测试：manual trigger 前后 official latest 字节内容保持不变。

### P0-7 新浪必需字段缺失被静默归零

**位置**

- `backend/plugins/principal_capital/sources/sina.py:40-46`
- `backend/plugins/principal_capital/sources/sina.py:79-112`

**证据**

`_to_float()` 对空值、`-` 和非法字符串返回 0.0。r0/r1 等必需资金字段全部缺失时，函数仍返回主力净流入 0、占比空的 provisional 行。该行会被算作 received，既会制造假覆盖，也会产生静默假阴性。

**必须修复**

1. `_to_float()` 对非法输入返回 `None`。
2. 明确 required fields；任何 required 字段缺失或非有限数时拒绝该行，并记录结构化失败原因。
3. `trade`、`changeratio` 若非筛选必需字段，可保持 nullable，不能伪造为 0。
4. report 增加 `invalid_rows` 与按原因统计的 `rejected_rows`。

### P0-8 batch_timeout 不是实际墙钟上限

**位置**

- `backend/plugins/principal_capital/sources/sina.py:118-152`

**证据**

`as_completed(..., timeout=batch_timeout)` 超时后离开 `with ThreadPoolExecutor`，context manager 会等待正在执行的任务结束。复现中，4 个 0.25 秒任务、2 个 worker、声明 batch timeout 0.03 秒，函数实际耗时约 0.51 秒。

**必须修复**

1. 使用显式 executor，在超时时取消未开始任务，并执行 `shutdown(wait=False, cancel_futures=True)`。
2. 单请求 timeout 不得大于本轮剩余预算。
3. 分批提交任务，避免一次性创建全市场 future。
4. 用 monotonic deadline 约束调度与请求；报告实际 elapsed 和 timeout 数量。

## 4. P1 重要修复项

### P1-1 日内特征和哨兵只有纯函数，没有运行时接线

全仓搜索显示 `compute_intraday_features()`、`should_run_sentinel()`、`mark_sentinel_done()` 和 `evaluate_auto_fallback()` 只出现在定义或测试中。扫描只追加原始 observation，没有把 5 分钟增量、30 分钟滚动净流入和连续窗口写入候选、雷达池或报告。因此 M3 尚未完成。

修复要求：

- 每轮追加有效 observation 后计算 features，并写回候选和 pool 的 `latest_metrics`。
- 报告记录 warming 状态与原因。
- invalid/partial/cache/stale observation 必须中断连续段，不能先过滤后跨越该点配对。
- `_ensure_aware()` 对 naive datetime 按 v2 约定抛 `ValueError`，调用方必须显式传北京时区。
- `append_fund_observation()` 按 `code + batch_id` 幂等。
- 增加从 `run_principal_capital_scan()` 到 radar 消费端的集成测试，不能只测纯函数。

### P1-2 shadow/readonly 返回了旧 official 状态

状态合并只在 official 执行；之后三种模式都从已加载 state 导出 `*_candidates_current/today`。因此 shadow 报告中的当前候选可能仍是上次 official 数据，readonly 的数量和列表也可能互相矛盾。

修复要求：shadow 使用独立状态文件；readonly 不持久化，但需基于本轮结果构造自洽列表。任何模式不得读取旧 official 状态后冒充本轮结果。

### P1-3 缺少 M5 可追溯证据链

当前 latest 会被下一轮覆盖，history 主要记录触发信号，没有完整保存每轮影子审计。部署五天后无法回放证明“每个有效轮次均零假阴性”。

修复要求：保存有界的每日审计记录，至少包含 `batch_id`、truth 来源、universe、覆盖率、阈值及配置版本、候选集合摘要、假阴性代码、延迟、deadline 和 `valid_for_admission`。只有完整 `sina_full` 真值轮次计入验收；粗筛配置变化时连续五日窗口清零。

### P1-4 owner 标识无唯一 job 身份，冲突路径仍写正式报告

workflow 固定设置 `PC_OFFICIAL_OWNER=github_actions`。两个 GitHub Actions job 会被识别为同一个 owner，可以相互续租。发生真正冲突时，拒绝方仍调用 `write_report()` 覆盖正式结果。

修复要求：owner 使用 `${GITHUB_RUN_ID}:${GITHUB_RUN_ATTEMPT}:${GITHUB_JOB}`，CLI 显式传 `--owner-id`。owner conflict 只能写独立诊断文件/日志，不得更新 official latest、state、history 或 notified。

### P1-5 radar 无法区分“权威空池”和“状态不可用”

`buy_candidates_current=[]` 是合法的权威空结果，但现有逻辑把它当作字段缺失并回退到 legacy 列表；state 合法空池也可能回退旧报告，从而复活陈旧候选，甚至把旧 sell 集合混入 buy radar。

修复要求：返回 `None` 表示来源不可用，返回 `[]` 表示权威空。只在 schema v1 或 key 缺失时使用 legacy fallback；key 存在且为 list 时必须尊重空列表。

### P1-6 质量门禁按来源名称放行

`_evaluate_quality()` 只要 active source 为 eastmoney 就 accepted，但 Eastmoney 行没有可靠的 `source_time`。质量判定应基于每行数据契约、覆盖率、时效、重复率和缺失率，不能把供应商名称当质量证明。现有测试还把这一不安全行为固化为预期，需要同步改写。

### P1-7 report 不是原子写，state/report 缺少批次一致性保护

日内 state 使用临时文件加 `os.replace`，但 official 和 shadow report 仍直接 `write_text`。读取方可能看到半写 JSON；state 与 report 分开落盘，进程中断时可出现不同 batch。

修复要求：所有 JSON 使用统一原子写助手；读取组合数据时核验 `state.last_batch_id == report.batch_id`，不一致时返回 degraded/consistency_error，而不是混合展示。

### P1-8 workflow 忽略 finalizer 和扫描失败

workflow 对扫描与 finalizer 的非零退出统一 `|| echo ...忽略`，CLI helper 也没有把 `send_failed`、owner conflict 等关键状态映射为非零退出。CI 可能显示绿色但正式任务失败。
