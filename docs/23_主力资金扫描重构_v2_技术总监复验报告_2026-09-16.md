## 3. 第二轮仍存在的 P0 阻断项

### P0-R1：M5 准入记录会把 shadow 失败、漏检和超时批次记成有效

**位置**

- `backend/plugins/principal_capital/service.py:702-734`
- `backend/plugins/principal_capital/service.py:903-909`
- `backend/plugins/principal_capital/service.py:986-1046`
- `backend/plugins/principal_capital/pipeline.py:166-194`

**问题**

`audit.valid_for_admission` 在主流程中被直接赋值为 `truth.valid_for_admission`。它没有检查：

- bulk 是否抓取成功；
- `bulk.validation.valid` 是否为 true；
- 买卖侧 false negative 是否均为空；
- 整轮 deadline 是否满足；
- shadow 是否实际执行完成。

因此，`_run_bulk_shadow()` 返回 `shadow_error` 时，主流程仍可把 `valid_for_admission` 覆盖成 true；默认空 audit 又恰好是零漏检。实测结果：

```text
shadow_error_admission = shadow_error True
```

`_record_m5_audit()` 又只保存 truth 的有效标记，所以错误会进入正式五日证据。

`compute_m5_streak()` 还有两个独立错误：

1. 同一天只要有一个 valid 记录，就会忽略该日其它 invalid 轮次。实测同一天一轮失败、一轮成功，仍返回连续 2 日。
2. 按自然日递减，周五到周一会被周末打断。实测周五和周一均有效，周一 streak 仍为 1。

**必须修复**

每轮准入值必须由完整条件计算，不能复制 truth 标志：

```python
round_valid = all([
    truth.source == "sina_full",
    universe_verified,
    truth.coverage_ratio == 1.0,
    not truth.rejected_rows,
    bulk.status == "shadow_only",
    bulk.validation.valid,
    not audit.false_negative_buy,
    not audit.false_negative_sell,
    deadline_met,
])
```

每日有效条件必须是该交易日所有应执行轮次均有效、配置指纹唯一且全时段覆盖达标。连续天数必须使用项目交易日历，跳过周末和休市日。任何有效交易日中的 invalid 轮次都应使该日失败，不能先过滤 invalid 记录。

### P0-R2：M5 审计文件没有进入 snapshot，跨 job/跨日会丢失

**位置**

- `backend/plugins/principal_capital/config.py:121`
- `scripts/commit_screening_data.sh:54-57,109-127`
- `scripts/restore_screening_data.sh:47-53`

**问题**

审计写在 `data/principal_capital_m5_audit.json`，但 commit/restore 白名单没有该文件。GitHub runner 是临时环境，上午、下午和下一交易日的新 job 无法继承审计记录，因此无法形成连续五日证据。

**必须修复**

将下列文件加入 commit、restore 和清理/重建白名单，并增加 round-trip 测试：

```text
data/principal_capital_m5_audit.json
data/principal_capital_intraday_state_shadow.json   # 若部署 shadow 模式需要跨 job 连续状态
data/principal_capital_owner_conflict.json          # 若 watchdog 依赖该诊断
```

其中 M5 audit 是强制项；没有跨 job 持久化就不能启动 M5 计时。

### P0-R3：finalizer 在“pending 已落盘、进程中断”后仍会自动重发

**位置**

- `backend/plugins/principal_capital/intraday_state.py:171-207`
- `backend/plugins/principal_capital/intraday_state.py:567-597`
- `backend/plugins/principal_capital/service.py:1104-1114`

**问题**

默认未尝试状态和 SMTP 前已落盘状态都叫 `pending`。`should_finalize_session()` 只阻止 sent、delivery_unknown、explicit_failed，对带 `attempt_id` 的 pending 仍返回 ready。

如果进程在 `mark_summary_pending()` 落盘之后、异常处理之前被 kill，下次 finalizer 会再次调用 SMTP。实测：

```text
pending_retry_decision = {should_send: true, reason: ready}
```

现有 A07 只覆盖 Python 捕获到异常的情况，没有覆盖进程崩溃/强杀这一真正的不确定投递窗口。

**必须修复**

- 默认状态改为 `not_attempted`。
- `pending + attempt_id` 在重启读取时必须转换或解释为 `delivery_unknown`，禁止自动发送。
- 新增子进程/持久化状态测试：先写 pending 后直接退出，再启动 finalizer，断言 SMTP 不被调用。
- 为 `explicit_failed` 提供显式、可审计的人工重试参数；普通定时 finalizer 继续禁止重发。

### P0-R4：owner lease 不是原子获取，首次扫描期间仍可能双写

**位置**

- `backend/plugins/principal_capital/service.py:843-877`
- `backend/plugins/principal_capital/intraday_state.py:137-152`
- `backend/plugins/principal_capital/intraday_state.py:639-649`

**问题**

主流程先读取 state，在内存中调用 `acquire_owner()`，随后立即开始最长 90 秒的外部请求；lease 要到扫描后半段才随 state 一起保存。两个进程可以同时读取“无 owner”的旧 state，并同时通过 acquire。即使增加了唯一 owner 字符串，也没有形成互斥。

**必须修复**

- 在同一个文件锁临界区内完成 load → 检查 lease → 写入新 lease。
- 外部网络请求开始前必须已经原子持久化 lease。
- 增加两个进程同时抢占空 state 的测试，只允许一个成功。
- GitHub workflow concurrency 可以保留，但不能替代代码声明的 owner/lease 语义。

### P0-R5：主板 universe 仍可能把缺页清单当成完整清单

**位置**

- `backend/plugins/principal_capital/sources/sina_market.py:60-115`
- `backend/plugins/principal_capital/sources/sina_market.py:161-196`
- `backend/plugins/principal_capital/service.py:642-679`

**问题**

清单分页遇到单页连续失败后会 `continue`，只要其它页返回过代码，最终结果就被当成成功并写入缓存。strict 随后以这个缺页列表作为 requested universe，并可能得到 100% coverage 与 `valid_for_admission=true`。

这仍然属于“分母随上游缺失一起缩小”的原始问题，只是从资金流响应移动到了 universe 获取阶段。

**必须修复**

清单函数应返回 `codes + pagination_meta`，至少包含 failed_pages、terminal_page_seen、page_count、duplicate_count 和 completeness。终止页之前任何缺页都必须使 universe `verified=false`，不得写为新鲜权威缓存，也不得计入 M5；可以使用上一次经过验证的缓存，但必须明确标记版本和年龄。

## 4. 第二轮仍存在的 P1 重要问题

### P1-R1：round deadline 不包含 bulk shadow 耗时

**位置**：`backend/plugins/principal_capital/service.py:877-909`

`deadline_met` 在 truth 拉取后立即计算，之后才调用 bulk shadow。实测 bulk 人为耗时 1.1 秒、round deadline 1 秒，最终仍返回：

```text
deadline_excludes_bulk = 1.11 True
```

应在本轮所有数据获取和必要计算结束后计算 deadline，并把同一个结果用于 status、auto fallback 和 M5 admission。

### P1-R2：日内 features 已计算，但没有进入 radar pool

**位置**

- `backend/plugins/principal_capital/service.py:949-971`
- `backend/plugins/principal_capital/intraday_state.py:214-215`
- `backend/plugins/principal_capital/intraday_state.py:531-548`
- `backend/plugins/smart_money_radar/service.py:205-225`

主流程先把 features 写进旧 pool entry，随后 `select_radar_pool()` 又用没有 features 的原始 buy row 覆盖 `latest_metrics`。新成员同样只保留 `_METRIC_KEYS`，其中不含 features。实测刷新后：

```text
pool_features_after_refresh = None
```

radar 从 pool entry 的 `latest_metrics` 读取，因此 M3 的“特征被雷达实际消费”仍未完成。应在选池前把 features 合并进 buy row，或在选池后统一回填 pool entries，并增加 scan → state → radar 的端到端测试。

### P1-R3：首次无 state 的标记会永久让 radar 认为状态不可用

**位置**

- `backend/plugins/principal_capital/intraday_state.py:608-636`
- `backend/plugins/principal_capital/service.py:932-972`
- `backend/plugins/smart_money_radar/service.py:205-218`

首次不存在 state 文件时，`load_state()` 写入 `_source_unavailable=true`。成功扫描后保存 state 时没有清除该临时标记；以后加载仍然保留，radar 每次都返回 None 并回退旧报告。实测保存再加载后该值仍为 true。

成功形成有效 state 后必须清除 `_source_unavailable` 和已恢复完成的 warming 标记。更稳妥的做法是这些诊断字段只作为 load 返回元数据，不进入持久化业务 state。

### P1-R4：state/report 一致性检查把“state 缺失”当成正常

**位置**：`backend/plugins/principal_capital/service.py:434-448`

只有 `last_batch_id` 为真且与 report 不同才报错。completed report 存在但 state 缺失或 `last_batch_id=None` 时，会原样返回 completed。实测：

```text
missing_state_consistency = completed None
```

此外检查只覆盖原始 status=completed，带 batch_id 的 partial/degraded 报告没有统一校验。应把缺 state、空 last_batch_id、trade_date 不一致都视为 consistency error，并明确本地与远程 snapshot 的一致性策略。

### P1-R5：sentinel 仍未接入，auto fallback 在保存 state 后才赋值

**位置**

- `backend/plugins/principal_capital/intraday_state.py:556-564`
- `backend/plugins/principal_capital/service.py:969-991`

全仓搜索确认 `should_run_sentinel()` 和 `mark_sentinel_done()` 仍只存在于定义和单元测试。主流程没有使用 `CONFIG["sentinel_times"]`。

同时 state 在第 972 行保存，`state["auto_fallback"]` 在第 991 行才赋值，因而正式文件不包含刚触发的自动回退状态。应调整保存顺序并增加从扫描入口验证持久化结果的集成测试。

### P1-R6：watchdog 无法观察新的 owner conflict，也没有检查 finalizer 缺失

**位置**

- `backend/plugins/principal_capital/service.py:865-870`
- `scripts/principal_capital_watchdog.py:53-91,140-155`

owner conflict 已按要求改写到独立诊断文件，但 watchdog 仍只拉取 `principal_capital_latest.json`。所以新增的 `status == owner_conflict` 分支实际上没有数据入口。

watchdog 也没有读取 intraday state 的 summary 状态，无法检查午间/收盘 finalizer 未完成、pending 卡死或 delivery_unknown。应把 conflict 和 summary 状态加入 watchdog 输入及去重告警类型，并为对应时间窗口增加测试。

### P1-R7：A05 服务级 batch 重放没有真正实现或覆盖

`build_round_context()` 每次生成新的随机 UUID，扫描入口也不接受已有 batch context。现有 A05 仅分别测试纯函数的候选与 observation 幂等，没有验证同一 batch 重放时 audit cursor 不推进，也没有覆盖 report/history/M5 audit 幂等。

应允许内部重试复用 RoundContext，或明确删除“服务级重放”承诺；验收测试需从 `run_principal_capital_scan()` 入口执行同一 batch 两次并核对全部状态。

### P1-R8：辅助 JSON 仍有直接写入，manual 状态不会结束

**位置**

- `backend/plugins/principal_capital/service.py:129-132,494-523`
- `backend/plugins/principal_capital/router.py:22-28,47-63`

history 和 notified 文件仍直接 `write_text`，未使用统一原子写助手。manual trigger 只写 running 和 error；成功完成后不会把 manual status 更新为 completed，页面或运维侧会长期看到 running。

应统一使用 atomic writer，并让 background task 在成功、失败、取消时都写终态及 batch_id/shadow report 引用。
