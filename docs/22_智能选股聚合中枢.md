### 2.4 `read_snapshot_resilient` 规格（`backend/plugins/common.py` 新增）

```python
def read_snapshot_resilient(
    snapshot_name: str,
    timeout: float = 5.0,
    ttl_seconds: int = 600,   # 对应 HUB_REMOTE_TTL_SECONDS，0 = 不缓存
) -> dict:
    """
    优先级：本地文件 → raw.githubusercontent(data-snapshots) 兜底
    永不抛异常；失败返回 {"status": "no_data", "_source": "unavailable", "items": [], "reason": "..."}
    """
```

**URL 拼接规则**（远端命中时响应写入 `_source="snapshot"`）：

```
RAW_BASE = os.getenv(
    "GITHUB_RAW_BASE",
    "https://raw.githubusercontent.com/{GITHUB_USER}/{REPO}/data-snapshots"
)
url = f"{RAW_BASE}/reports/data_backend/{snapshot_name}_latest.json"
```

`GITHUB_USER` / `REPO` 同 `commit_screening_data.sh` 已有的仓库常量，不重复硬编码。`GITHUB_RAW_BASE` 可覆盖供本地调试。

**执行流程**：

| 步 | 操作 | 成功 | 失败 |
|---|---|---|---|
| 1 | 读 `reports/{snapshot_name}_latest.json` | `_source="local"` 返回 | 进入步骤 2 |
| 2 | `reports/data_backend/{snapshot_name}_latest.json` | `_source="local"` 返回 | 进入步骤 3 |
| 3 | chip 专属判断：`config.chip_remote_fetch=false` | 返回 `_source="local_only"` + `no_data`，**不发网络** | — |
| 4 | `httpx.get(url, timeout=timeout)`，HTTP 200 且 JSON 合法 | `_source="snapshot"` + 可选写磁盘 TTL | 返回 `_source="unavailable"` + `reason="remote_fetch_failed:<code/err>"` |

**关键约束**：
- `timeout=5.0` 硬上限；云端首请求实测 100–500ms，5s 是极端降级保护值。
- 函数本身**不做内存缓存**——内存缓存在各 router 的 `_latest_cached()` 一层完成，不重复。
- chip 快照从不提交 data-snapshots，步骤 3 拦截防止无效远端请求。
- 磁盘 TTL 缓存路径：`reports/.cache/{snapshot_name}_remote.json`（与 `reports/` 同目录，不进 git）。

## 4. 聚合算法规格（全部纯函数，单测覆盖）

### 4.1 输入快照（读函数 `read_snapshot_resilient`，顺序：本地文件 → raw 兜底）

| 策略 | 快照文件 | 正常结构（G9） | 旧格式兼容 | 云端预期 |
|---|---|---|---|---|
| tech | `tech_indicators_latest.json` | `golden_pool/oversold_pool/multi_hit_pool/items` | 顶层仅 `items`（现状实测） | raw 兜底 |
| trend | `trend_strength_latest.json` | `strong_pool/leader_pool/items` | 顶层仅 `items` | raw 兜底 |
| pattern | `pattern_scanner_latest.json` | `platform_pool/gap_pool/dual_pool/items` | — | raw 兜底 |
| chip | `chip_scanner_latest.json` | `strong_pool/tight_control_pool/items`，`local_only/approx` | — | `no_data`(需本地运行) → 策略不可用 |

**可用性判定**（`strategies[<k>].available`）：
- 快照 `status == "completed"` 且能从 `items` 提取到非空 rows → `available=true`；
- `status in (no_data, empty, skipped)` → `available=false`，不抛异常；
- 有 `items` 但缺 pools → `degraded=true`（旧格式），pools 相关计数用 items 现算；
- 快照拉取失败（本地无 + raw 失败）→ `available=false` + `reason="snapshot_unavailable"`。

### 4.2 合并去重 `union_table(snaps) -> list[dict]`

- 主键：`code`（6 位补零字符串）。同一 code 在多个策略命中 → 合并为一行，`hit_strategies = 命中策略数`，`resonance = hit_strategies >= HUB_RESONANCE_MIN_HIT`。
- 基础字段取值优先级：`name`（首个非空）、`price/change_pct/total_amount`（**当日一致性**：按 `tech → trend → pattern → chip` 优先取 `is_intraday=0` 行的值；若全部为 intraday，取首个）。
- 每策略命中行原样保留进 `hits.<k>`（不丢字段，前端详情用）。
- 行内去重：单个快照内 `items` 与各 pool 的重复行只取一次（现状 115 重复行在此消除）。

### 4.3 pct 兜底 `recompute_pct(items, score_key)`

- 优先使用各插件已写入的 `*_score_pct`；
- 若该策略所有命中行均无 pct（旧格式快照），用该策略 items 的 `score_key`（tech→`tech_score`，trend→`trend_score`，pattern→`pattern_score`，chip→`chip_score`）做当日百分位：`pct = bisect_right(sorted_scores, score)/len*100`（与 18 方案 G8 同口径）；
- 仍不可得 → 该策略对该行贡献 0 且 `pct.<k>=null`。

### 4.4 统一分 `compute_hub_score(row, weights) -> float`

```
hub_score = Σ_k ( weights[k] × pct[k] ) × 100 / Σ_available(weights)
          （pct ∈ [0,100]；缺失策略权重重分配到可用策略，weights 归一化，仿 15 方案 d3_degraded）
hub_score_pct = 当日 hub_score 百分位（同 4.3 口径，跨日可比）
```

- 权重默认：`tech 0.30 / trend 0.25 / pattern 0.20 / chip 0.25`（env `HUB_W_TECH/HUB_W_TREND/HUB_W_PATTERN/HUB_W_CHIP` 可覆盖，负值/非数拒绝；总和自动归一化）。
- 后续校准接口：06 因子实验室产出 IC 后改 env 即可，**本方案不接**。

### 4.5 排序与 tie-break（服务端统一）

`sort` 白名单 → 主键降序/升序；**tie-break 固定二级键**：`hub_score → hit_strategies → code`（保证翻页稳定，不因快照重写漂移）。

### 4.6 门控 `apply_gates(items, zt_codes, cfg) -> (items, gate_report)`

1. **当日涨停剔除**（`HUB_EXCLUDE_LIMIT_UP=1` 默认开）：读 `reports/data_backend/zt_pool.json`（本地优先，raw 兜底）取当日代码集合；命中即剔除。
   - zt_pool 不可用 → **跳过门控**，`zt_gate_applied=false` + `zt_gate_reason="zt_pool_unavailable"` 显式标注（不伪造，不静默）。
2. **市场过滤**：`code` 前缀 300/301/688 + ST 名称，按 `market` 参数应用（复用 `common.market_filter` 口径，不重写判断）。
3. **成交额下限**：`total_amount < HUB_MIN_AMOUNT`（默认 0，即不启用）剔除，字段缺失不剔除（只在有值时判断）。

### 4.7 交叉 badges（只读展示，不参与分数；缺失省略，绝不编造）

| badge 键 | 来源快照（缺失即跳过该键） | 输出字段 |
|---|---|---|
| `fund_flow` | `principal_capital_latest.json` | `main_net_inflow / main_inflow_ratio / source` |
| `tier_state` | `tier_flow_latest.json`（按 code 匹配） | `state ∈ {吸筹,出货,拉升}` |
| `radar` | `smart_money_radar_latest.json`（按 code 匹配） | `strength / source` |

- 匹配不上或来源不可用 → 该行无该 badge 键；`badges_missing` 计数进 `signal_counts` 供前端显示覆盖率。
- 后续可扩展：emotion（01）/board（05）/l2_features（方案二），仅加配置项，不改核心。

### 4.8 图表预计算 `precompute_charts(pool_codes, cfg)`

- hub 聚合时 K 线缓存仍热（同一进程刚扫完全市场），对最终榜单**前 `HUB_CHART_PRECOMPUTE_N=40` 只**调用既有各插件的 `*_series_full` 纯函数生成系列（MACD/KDJ/RSI/BOLL/MA），写入**独立快照** `smart_picker_charts_latest.json`（`CHARTS_SNAPSHOT_NAME`）的 `charts.{code}` 键；**不额外拉任何网络**。
- 超出 40 的票：详情接口走 on-demand（当日进程内 `get_kline_cached` 兜底 + `cached:false` 标注）。

### 4.9 图表独立快照 `smart_picker_charts_latest.json`（与 §6.3 响应同构）

**施工实测修正**：40 只 × 80 bar 全序列 JSON 实测 ~2.2MB，与主快照 ≤150KB 预算冲突 → 图表**不嵌主快照**，独立双写 `CHARTS_SNAPSHOT_NAME`（默认 `"smart_picker_charts"`）。主快照顶层只保留引用字段 `charts_precomputed:{count,n,codes}`。

`smart_picker_charts_latest.json` 顶层结构：

```json
{
  "status": "completed",
  "run_at": "2026-09-08T15:19:47+08:00",
  "date": "2026-09-08",
  "count": 40,
  "charts": {
    "600519": {
      "records": [ ... 80 bar OHLCV，与 §6.3 records 同构 ... ],
      "series": {
        "ma":   { "ma5": [...], "ma10": [...], "ma20": [...], "ma60": [...] },
        "macd": { "dif": [...], "dea": [...], "hist": [...] },
        "kdj":  { "k": [...], "d": [...], "j": [...] },
        "rsi":  [...],
        "boll": { "mb": [...], "ub": [...], "lb": [...] }
      }
    }
  }
}
```

- 键为 6 位 code 字符串，值与 `/smart-picker/{code}/chart` 响应的内层（records + series）一致（§6.3）。
- 仅存前 `chart_precompute_n=40` 只；`charts` 缺 code 键时 `/chart` 端点走 on-demand（§6.3 步骤 2）。
- 读取：`/chart` 端点经 `_charts_cached()` 读该快照的内存缓存（进程内一次性加载，逐 code 取用 <1ms）；云端冷启动首请求一次 raw 兜底拉取。

### 7.4 绩效回填算法（无前视，硬约束）

**交易日历来源**：直接从 K 线 bar 序列推导，不依赖外部日历接口。

```python
def trading_days_after(bars: list[dict], anchor_date: str, k: int) -> str | None:
    """
    bars: 按 date 升序排列的 K 线列表（来源 fetch_historical，已过滤非交易日）
    anchor_date: 信号日期（D），必须在 bars 内
    k: 第 k 个交易日（k=1 即下一交易日）
    返回目标日期字符串；anchor_date 不在 bars 内或 bars 不够长 → None
    """
    dates = [b["date"] for b in bars]
    try:
        idx = dates.index(anchor_date)
    except ValueError:
        return None
    target_idx = idx + k
    return dates[target_idx] if target_idx < len(dates) else None
```

- 原理：东财 `fetch_historical` 返回的 bar 序列**本身就是交易日序列**（已剔除休市/停牌缺 bar 日），无需维护独立日历文件，无网络依赖，无除权/停牌歧义。
- 停牌处理：若 `bars` 在 anchor 之后不足 k 条（连续停牌或数据截断） → `data_missing=1`，跳过该窗口。
- 单测验证：构造含已知交易日序列的 mock bars，直接断言 `trading_days_after` 返回值，无任何外部依赖。

```
refresh_perf(compute_date=R, cfg):
  候选 = picker_perf_daily 中 signal_date ∈ 最近 HUB_PERF_LOOKBACK_DAYS 个交易日 且存在未填窗口
  对每个 (signal_date=D, code):
    bars = fetch_historical(code, days=130)          # 复用 get_kline_cached
    定位 D 的 bar（date==D）；缺 → data_missing=1，跳过
    对每个 window k ∈ {1,3,5}:
      target = trading_days_after(bars, D, k)        # 见上方函数，非自然日
      if target is None or target > R: 跳过（未到期或数据不足，不填）
      if bars 含 target: t{k}_close/ret 填入, t{k}_filled=1
      else: data_missing=1（停牌/无 bar，ret 为 null，不计入汇总）
```

- 单测：删除 R 之后的 bar 后，全部 `filled` 字段与结果不变。
- 口径标注：`close` 取 `fetch_historical` 默认口径（不复权），**除权日收益可能失真**——`raw_json` 留全字段，后续如需复权口径在 06 因子实验室统一处理，本方案不改口径。

## 12. 风险与限制

| # | 风险 | 缓解 |
