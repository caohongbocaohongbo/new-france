# 01 情绪周期与连板梯队 — 产品开发技术方案

## 1. 目标与定位

把现有“涨停池”升级为短线市场水温计。回答三个实操问题：
- 今天市场情绪处于冰点 / 修复 / 发酵 / 高潮 / 退潮的哪一阶段；
- 今天该打首板、做龙头、低吸还是空仓，建议多少仓位；
- 连板梯队是否健康，谁是龙头、谁在掉队。

优先级：P0。依赖现有 `eastmoney_zt` 涨停池，原料最现成，短线参考性最强。

## 2. 产品方案

### 2.1 用户场景
交易日盘后 15:10（已有 daily-screening cron）自动产出，次日 09:25 竞价前可查。用户打开“情绪周期”页，先看情绪温度计，再看昨日涨停今日表现、连板梯队与操作结论。

### 2.2 页面模块
- 情绪温度计：冰点 → 修复 → 发酵 → 高潮 → 退潮 五段，显示当前得分与历史分位。
- 昨日涨停今日表现：溢价率、晋级率、炸板率、大面率。
- 连板梯队：首板 / 2 板 / 3 板 / 最高板家数，龙头、卡位、掉队标记。
- 操作结论：低吸 / 打首板 / 做龙头 / 空仓 + 建议仓位区间。

### 2.3 指标口径
- 昨日涨停溢价率：昨日涨停股今日竞价买入 / 开盘买入 / 收盘买入的平均收益。
- 晋级率：昨日 N 板股今日成功晋级 N+1 板的比例。
- 炸板率：炸板次数 > 0 的涨停股 / 全部涨停股。
- 大面率：涨停买入后当日最大回撤 > 5% 的比例。
- 空间板高度：当日最高连板数。

## 3. 技术方案

### 3.1 数据源
- 当日涨停池：`backend/agents/layer1_data_collector/sources/eastmoney_zt.py::fetch_zt_pool`。
- 历史涨停池回补：Tushare `limit_list_d`（若配置 TOKEN）或 akShare `stock_zt_pool_em` 按日回补。
- 次日表现：历史 K 线 `historical_kline.py` 或次日行情快照。

### 3.2 算法

情绪分 = 涨停家数 z-score × w1 + 空间板高度分 × w2 + 晋级率 × w3 + (1 - 炸板率) × w4 + 昨日涨停溢价 × w5 + 指数涨跌 × w6。

先给经验初值，累计 60 个交易日样本后，用历史分位校准阈值（见 06 因子实验室）。

### 3.3 调度
- 盘后 15:10 每日任务内新增 `emotion` 阶段。
- 每日只跑一次，产出 JSON，避免盘中重复计算。

### 3.4 容错
- 涨停池为空 → 输出 `status=no_data`，页面显示空态，不伪造情绪分。
- 东财与 Tushare 交叉验证差异超过阈值 → 打 `degraded` 标记。

## 4. 数据存储方案

### 4.1 SQLite 表

```sql
CREATE TABLE limit_up_daily (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  date TEXT NOT NULL,
  code TEXT NOT NULL,
  name TEXT,
  board_height INTEGER DEFAULT 0,
  seal_time INTEGER,
  break_count INTEGER DEFAULT 0,
  first_seal_time INTEGER,
  industry TEXT,
  concept TEXT,
  is_trap INTEGER DEFAULT 0
);
CREATE INDEX idx_lu_date ON limit_up_daily(date);
CREATE INDEX idx_lu_height ON limit_up_daily(date, board_height);

CREATE TABLE emotion_daily (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  date TEXT UNIQUE NOT NULL,
  metrics_json TEXT NOT NULL,
  score REAL,
  regime TEXT,
  created_at TEXT
);
```

### 4.2 文件快照
- 聚合结果物化 `reports/emotion_latest.json`。
- 同步 `reports/data_backend/emotion_latest.json` 并提交 `data-snapshots` 分支兜底。

### 4.3 保留策略
- SQLite 保留最近 3 年，每季度归档一次。
- JSON 只保留 latest，历史以 SQLite 为准。

## 5. 数据读取方案

- `GET /api/v1/emotion/latest`：读 `emotion_latest.json`，不做现拉，秒开。
- `GET /api/v1/emotion/history?days=90`：走 SQLite `date` 索引。
- `GET /api/v1/emotion/ladder?date=YYYY-MM-DD`：连板梯队明细。

前端页面读 latest 渲染温度计与梯队；历史曲线点“历史”再请求 history。

## 6. 与现有系统集成

- 新增 `backend/plugins/emotion_cycle/`，包含 `config.py / service.py / indicators.py / router.py / notifier.py / tests/`。
- `main.py` 注入 router（try/except）并加 `--run-emotion-once` CLI。
- 复用 `eastmoney_zt`、`historical_kline`、`data_backend.snapshots` 与邮件 `principal_capital.notifier.send_email`。

## 7. 测试与验收

- 单元测试：指标口径（溢价率/晋级率/炸板率/大面率）、情绪分边界、regime 迁移。
- 集成测试：空涨停池 no_data、东财失败降级 Tushare。
- 验收：连续 5 个交易日产出，情绪曲线与肉眼判断一致，页面秒开 < 500ms。

## 8. 上线与运维

- Render cron / GitHub Actions daily-screening 增加 emotion 阶段。
- 生成物只提交 `data-snapshots`，不污染 main。
- 首次上线跑历史回补脚本，补齐近 60 个交易日涨停池。

## 9. 风险与限制

- 情绪分阈值初期靠经验，需样本校准，不可直接当作未来收益承诺。
- 涨停池含 ST/退市股需单独过滤口径。
- 节假日 / 半日市需交易日历校准（当前 `trading_session.py` 尚未接交易日历）。

## 10. 里程碑

1. M1：历史涨停池回补 + `limit_up_daily` 落库。
2. M2：指标计算 + 情绪温度计 + 连板梯队。
3. M3：页面 + 邮件摘要 + 数据快照兜底。
