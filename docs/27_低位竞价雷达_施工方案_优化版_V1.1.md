## 0. 修订结论与施工红线

### 0.1 保留、调整、禁止

| 类别 | 决策 | 原因 |
|---|---|---|
| 保留 | 复用插件16低位池、插件13竞价因子思路；插件28独立编排 | 不重复建造选股/交易日历/通知能力 |
| 保留 | Python 常驻 daemon、内存滑窗、SQLite、JSON 快照、REST | 100–600只股票无需引入 Kafka/Redis |
| 调整 | 竞价期数据契约以**虚拟参考价/虚拟匹配量/虚拟未匹配量**为核心 | 普通五档、累计成交量不能直接当竞价量 |
| 调整 | 区分 `PRELIMINARY` 与 `CONFIRMED`，9:25以后验证最终撮合数据 | 不把09:24:5x预测值冒充开盘成交数据 |
| 调整 | 盘前冻结低位池；GET纯读；常驻增量计算；SQLite Outbox独立推送 | 降低关键路径延迟与漏发概率 |
| 调整 | 信号按质量分级、统一单位、缺失因子重归一化 | 防止“快速但错误”的榜单 |
| 禁止 | 仅凭HTTP 200就认为行情新鲜；未验证字段强行填0 | 避免伪实时和假强弱 |
| 禁止 | 9:20以后未匹配量减少就认定撤单；五档和未匹配量画等号 | 不符合交易阶段语义 |
| 禁止 | 查询接口触发低位池重算或实时第三方请求 | 避免读路径阻塞竞价采集 |
| 禁止 | 发送外部网络请求、历史帧批量写库阻塞9:25最终确认 | 保障查询与推送时效 |

### 0.2 上线前五项 Gate（任一失败不得正式发布“已确认竞价榜单”）

1. **G1 数据源核验**：至少两个完整交易日采样；沪、深不同股票核对时间戳、单位、字段含义；与具备竞价行情揭示的可信终端做样本对照。未确认的字段不参与正式评分。
2. **G2 最终撮合核验**：取得9:25后真实可验证的开盘价和成交量；不能确认时标为`UNCONFIRMED`，不输出`CONFIRMED`。
3. **G3 全链路状态机**：进程重启、源超时、写库失败时能恢复；同一日同一策略/信号版本只能有一份逻辑最终信号。
4. **G4 推送可靠性**：SQLite Outbox落库、各通道独立状态、幂等键、失败重试、操作日志；SMTP接收≠收件人收到。
5. **G5 可观测性能**：能看见行情源时间、接收、评分、发布、Webhook接受、SMTP接受各时间点及P50/P95/P99。

### 0.3 P0 与 P1 边界

- **P0必须做**：数据字段验证、时间语义、盘前准备/冻结、5秒全池采集（允许先不热点高频）、增量评分、最终确认状态、快照原子发布、Outbox邮件/Webhook推送、只读REST、性能与故障验收。
- **P1再做**：1–2秒热点池采集、竞价时间线前端、SSE、9:30后分时提醒、历史竞价量比自学习、复盘/模拟盘。
- **明确不做**：重构13/16插件、全市场逐笔重建、自动交易、Kafka/Redis/K8s。首次版本不要因“多源支持”牺牲可验证性：**先验清一个源，再做备用源**。

## 1. 与原稿的兼容、需核验事项

### 1.1 保持的依赖与已有约定

- 低位池：`backend/plugins/low_position_scanner/service.py::run_low_position_once`；`read_snapshot("low_position")`；`low_score`及`is_low_position`等历史选股指标。
- 竞价参考：`backend/plugins/smart_money_radar/auction.py` 和 `store.py`，只复用已证实正确的纯函数；竞价源解析仍在新插件独立实现。
- 交易时间/日历：`backend/services/trading_calendar.py`，`backend/api/router_system.py::trading_session_status`。
- 存储：`backend/db/plugin_models.py`、`backend/plugins/common.py` 的快照工具、SQLite。
- 邮件：`principal_capital/notifier.py::send_email`；现有邮件基础设施可复用，但**必须检查同步阻塞、超时、返回值语义和副作用**。
- CLI：`backend/main.py` 追加 `--run-auction-radar-once`、`--run-auction-radar-daemon`、`--run-auction-radar-review`。

### 1.2 实施前先验证的三个原稿“既有缺陷”

1. 原稿称13号`scheduler.py`读取`session`而上游返回`market_session`：对照**当前仓库**函数签名/调用栈/测试核验；若成立，做兼容读取并加回归测试，否则禁止重复修复。
2. 原稿称腾讯解析缺`vol/amount/turnover/volume_ratio`：先抓取**真实竞价期原始报文**，确认字段索引、单位、所处交易阶段和是否实际更新；字段存在**不等于**就是虚拟匹配量。即便新增解析也必须声明语义。
3. 原稿称13号盯的是`principal_capital`≤40只而不是16号低位池：代码核对后，由新插件显式绑定16号池，避免改变13号原有业务。

### 1.3 对原稿关键断言的纠正

- 原稿`bid_vol_total - ask_vol_total`并不能直接推出交易所的“虚拟未匹配量”；无验证供应商字段时应为`null`。
- 原稿`auction_turnover(vol, float_shares)=vol*100/float_shares`若`vol`为“手”，相对百分比会少一个100倍数量级：内部先统一“股”。
- 原稿`hist_avg_daily_volume/240分钟`不可无差别充当“历史9:25竞价均量”；无历史同期数据就降低覆盖率并标识。
- 原稿`risk_score=0`只降低总分15%，并不能视为强风险过滤；硬过滤和软惩罚必须分离。
- 原稿9:20以后`bid`下降视为撤单并不严谨。沪市交易规则明确9:20–9:25不接受撤单申报；深市也必须按现行规定和实际行情语义核验。
- 原稿`GET /pool`→`load_low_pool()`，而其实现允许过期时重算：更改为查询纯读和后台准备职责拆分。
- 原稿`/{code}`与`/review`可能有动态路由遮蔽；统一改为`/stocks/{code}`。
- 原稿`AuctionStore`为进程内存；API与daemon若分属不同进程，必须通过原子快照/数据库交换状态，不能互读Python内存。

## 2. 成功标准与数据时序（北京时间）

| 阶段 | 时刻 | 必须完成的任务 | 失败处理 |
|---|---|---|---|
| T-1盘后 | 15:10之后 | 复用16生成可追溯候选池、`asof_trading_day`、筛选口径/数据源 | 告警，保留历史产物但不得冒充当日 |
| T盘前 | 09:10 | 加载上一**有效交易日**池；装载流通股本、历史基准、风险标签；配置和数据源健康检查 | 进入`PREPARE_FAILED`，重试仅在准备窗 |
| T盘前 | 09:14:30 | 完成池冻结，`pool_hash`固定；记录股票列表及来源日期 | 仍无可靠池则`SKIPPED_NO_POOL` |
| 竞价阶段1 | 09:15–09:20 | 全池轮询、预判、发现申报变化；记录源数据 | 可降级，但标记质量 |
| 竞价阶段2 | 09:20–09:25 | 持续轮询、增量评估、近末端优先刷新；**不把量价变化直接解释成撤单** | 源失效则`DEGRADED` |
| 预测榜单 | 09:24:45–09:24:59 | 将最新有效报价形成`PRELIMINARY`榜单；不得标注最终开盘价 | 可在只读接口显示，不发送“最终确认”通知 |
| 撮合确认 | 09:25:00之后 | 在预算窗口内获取并验证最终开盘价/量（最终数据未必于09:25:00立即可用） | 超时标`UNCONFIRMED`，只做故障/未确认提示 |
| 发布 | 取得确认之后 | 增量更新、硬风险过滤、冻结版本号、提交持久化信号及任务、原子发布快照 | 崩溃后可恢复 |
| 通知 | 快照可查之后 | 邮件与Webhook独立异步提交、写入通道结果 | 失败重试，不阻塞榜单 |
| 盘后 | 15:10之后 | 按原稿复盘（P1），回填价格表现、策略版本 | 缺数据不补造 |

**交易阶段状态机**（每个交易日/策略版本唯一）：

```text
INIT → PREWARMING → POOL_FROZEN → POLLING
                               ├─> PRELIMINARY → WAITING_FINAL
                               │                       ├─> CONFIRMED → PUBLISHING → PUBLISHED
                               │                       ├─> UNCONFIRMED (超时/源无证据)
                               │                       └─> FAILED (数据严重不一致)
                               └─> DEGRADED / SKIPPED_NO_POOL
PUBLISHED → NOTIFYING → NOTIFIED / PARTIALLY_NOTIFIED / NOTIFY_FAILED
```

- `CONFIRMED`指**所要求的最终竞价核心字段具有足够证据**；不代表模型预测一定正确。
- 9:25以后返回的行情如果只有价格、没有可验证的最终竞价量，须允许`confirmed_fields=["open_price"]`等字段级证据，同时将信号总体状态置为`PARTIAL`或`UNCONFIRMED`（由正式发布所需字段配置决定）。
- 不得以`datetime.now()>=09:25`直接将最新旧帧升级为`CONFIRMED`。
- 允许局部股票状态不同：最终榜单只使用字段充足且质量合格者；整体提供`confirmed_count/unconfirmed_count`。

## 3. 数据采集契约：先准确，后快

### 3.1 统一数据结构（typed dataclass / Pydantic，独立于供应商）

```python
class AuctionQuote:
    trade_date: str
    code: str
    name: str | None
    source: str                       # tencent | eastmoney | tdx ...
    source_timestamp: str | None      # 无源时间时必须为None，不得造时间
    received_at: str                  # 北京时间有时区偏移
    market_phase: str                 # PRE_AUCTION | NON_CANCEL | FINAL | UNKNOWN
    indicative_price_yuan: float | None
    indicative_match_shares: int | None
    indicative_unmatched_shares: int | None
    unmatched_side: str | None        # BUY|SELL|UNKNOWN；无法确认保持UNKNOWN
    final_open_price_yuan: float | None
    final_match_shares: int | None
    prev_close_yuan: float | None
    float_shares: int | None
    source_volume_raw: float | None   # 只用于审计，不默认是竞价匹配量
    source_amount_raw: float | None
    source_volume_unit: str | None    # lot | share | unknown
    price_limit_up_yuan: float | None
    price_limit_down_yuan: float | None
    raw_payload_hash: str
    quality: str                      # VALID | PARTIAL | STALE | INVALID
    quality_reasons: list[str]
    confirmed_fields: list[str]
```

**字段原则**：

- `indicative_*`用于9:15–9:25预测；`final_*`只能由最终撮合口径证据赋值。
- `indicative_match_shares`不得从一般行情`vol`字段强行推断；`indicative_unmatched_shares`不得从买卖五档简单相减得到。
- 保留供应商原始值、单位、报文哈希用于追溯，优先落本地采样文件用于验证；日志中不得泄露令牌。
- 如果供应商无法提供真实未匹配量，把对应因子从有效权重集合移除，不以0伪造。
- 绝不把本地`received_at`写成`source_timestamp`；如果无法度量真正传输延迟，标`source_lag_unknown`。

### 3.2 数据源验证表（施工阻塞项）

| 来源 | 必须实测并记录 | 正式可用条件 |
|---|---|---|
| 腾讯 `qt.gtimg.cn` | 9:15/9:19:5x/9:20/9:24:5x/9:25+样本；GBK、字段位置、字段更新时间、量单位 | 被实际验证的字段才进入模型；常规五档不能自动当未匹配量 |
| 东财 `push2` | 同样时段样本；`f2/f3/f5/f6/f8/f10`在竞价期含义及刷新时间 | 只补其支持并经验证的字段；不同口径不得混算 |
| TDX | 盘前虚拟量/价相关返回字段、服务器时间、网络可用性、断连行为 | 仅在具体字段实测通过后可作为替代源 |

**执行要求**：新增`tools/auction_radar_probe.py`或插件内`probe.py`，允许交易日只读采样，输出`csv/jsonl`，包含供应商、交易阶段、源时间（若存在）、接收时间、关键原始字段、规范化值、来源说明。至少两个完整交易日，覆盖沪/深、普通主板及不同涨跌停价格情形。源能力不足时允许先发布“**有限因子竞价雷达**”，但必须公开缺失因子、降低评分置信度，不允许用未验证数据填充。

### 3.3 数据质量门禁 `QuoteQualityGuard`

```python
validate_quote(quote, trade_day, phase, previous_quote) -> QualityResult
# result: quality, reasons, allowed_fields, lag_ms|None, fallback_required
```

规则：当前交易日与股票代码匹配；时间戳不倒退；正价格、有效数量、单位可解释；对应板块/风险类型价格限制合理；关键字段来源一致；对疑似旧行情/跨源口径冲突降级。不同数据源更新频率与时间精度不一致时不强行设固定绝对延迟；以**每源经实测确定的 freshness_sla**决定`STALE`。价格限制要依据证券所属板块、ST状态和是否处于无涨跌幅限制阶段，不用统一`gap>9%`代替全部股票。

跨源切换必须保留每只股票`source`和`quality`，不能仅把整个快照标成一个来源。若回退源缺少关键竞价字段，对该股票取消对应因子并标明`PARTIAL`，不能使用之前主源旧值伪装新值。

## 4. 盘前股票池与采集调度

### 4.1 将读池与重算彻底分离

```python
def read_low_pool_snapshot(trade_day: date) -> PoolSnapshot:
    """纯读；验证asof_trading_day==prev_trading_day(trade_day)、状态、字段、hash。
    无网络、无低位选股重算；异常返回明确status。"""

async def prepare_low_pool(trade_day: date, *, allow_regenerate: bool) -> PoolSnapshot:
    """只在盘前/盘后后台作业执行；必要时触发16号插件。"""

async def freeze_pool(trade_day: date) -> FrozenPool:
    """锁定code列表/low_score/历史基准/风险标签/池来源版本/池哈希。"""
```

- 盘前读取**上一有效交易日**的盘后池，不误把T-1日期认定为过期；节假日用`prev_trading_day`判定。
- 9:14:30后不可自动改变当日池成员；强制手动更新仅限受控CLI，生成新版本并完整审计，默认关闭。
- 09:15后所有`GET`不得触发第三方HTTP/低位重算。
- 若关键历史因子缺失，按缺失因子降级，不把无量数据计算成高量比。

### 4.2 P0稳定采集：全池5秒，防重叠优先

- 固定`batch_size <= 60`为初值而非接口保证；并发≤4为配置初值；按实测响应尺寸/429/超时调优。
- `single_flight`保护：上一轮采集未结束，下一轮不并发重叠；记录`skipped_poll_rounds`。
- `poll_deadline`：设置每轮总预算、批次超时和取消策略；旧响应不得覆盖新帧。
- 分离网络`fetch`、字段`normalize`、质量`validate`、增量`score`，避免异常阻断全池。
- 失败批独立处理；返回全池覆盖率、当前新鲜行情覆盖率以及每股票最新有效帧时间。

### 4.3 P1可选：全池 + 热点池自适应

- 基础池：100–600只，每5秒尽量全覆盖。
- 热点池：根据**最近有效**排名、量价变化及排名边界选择最多60只，每1–2秒采集（须确认源允许/确有刷新价值）。
- 09:24:50后优先刷新热点、排名边界及刚刚缺失的股票，保留全池最后有效覆盖。
- **不可仅用热点池确定最终TopN**：最终榜单还要检查全池数据是否足够新鲜、是否有遗漏强势标的。

### 4.4 09:25最终确认调度算法

```python
async def finalize_once(trade_day, strategy_version):
    run = await claim_run_once(trade_day, strategy_version)  # DB唯一键/抢占
    if not run.claimed:
        return await read_published_result()
    preliminary = store.get_latest_valid_ranking()
    deadline = monotonic() + cfg.final_wait_max_s
    while monotonic() < deadline:
        final_quotes = await collector.fetch_final_candidates_and_boundary()
        quality = verify_final_quotes(final_quotes, preliminary)
        if quality.minimum_publishable:
            return await publish_final_result_atomically(quality, run)
        await asyncio.sleep(cfg.final_retry_interval_s)
    await mark_unconfirmed_and_alert(run, reason="final_market_data_not_verified")
```

- `final_wait_max_s`初值15秒，**不意味着9:25:15一定取得数据**；应以9:25后真实数据可得性为准。
- 最终确认应有`min_confirmed_count`/`required_fields`门槛：达不到就停发正式榜单，可发送“未确认”故障通知。
- 已正式发布不可被较旧源结果覆盖；若后来取得修正，应创建`revision=2`更正版本和独立通知策略，不静默篡改。

## 5. 竞价因子、评分和风险口径

### 5.1 单位规则

内部标准单位：人民币元、股、百分比的数值（例如2.5代表2.5%）。供应商提供“手”时，每手=100股按适用证券单位明确转换。

```python
match_amount_yuan = indicative_price_yuan * indicative_match_shares
auction_turnover_pct = indicative_match_shares / float_shares * 100  # 若确是匹配股数
final_amount_yuan = final_open_price_yuan * final_match_shares
```

注意：`indicative_match_shares`是预测可匹配量，9:25前**不是已经发生的成交量**。仅对有效数据计算。

### 5.2 竞价相对放量

优先：`final_match_shares / median(过去N个可用交易日9:25最终竞价匹配股数)`；盘前预测阶段采用相同时间段历史样本（须采样数据库足够完整）。

- 无历史同期竞价数据：标`auction_relative_volume=null`；可以展示供应商已验证的“量比”但不得与历史竞价量比混为一个字段。
- 禁用原稿`近20日日均量/240分钟`直接替代9:25历史基准。
- P0若历史竞价数据尚未积累：采用已验证的竞价金额、价格、量趋势及低位特征进行**有限因子评分**，明确标识评分版本`limited_v1`；历史相对量比到P1开放。

### 5.3 评分权重与缺失因子

原稿参考权重：竞价价差0.25、量比0.30、换手0.15、金额0.15、未匹配0.15；总分低位0.35、竞价0.50、风险0.15。该权重只是初始假设，需复盘校准。

建议P0评分顺序：

1. 检查有效数据、交易阶段与证券过滤条件；硬风险失败直接排除正式榜单，保留审计原因。
2. 按**已验证且非空**的因子计算0–100分；缺失因子做权重重归一化，但不足最低覆盖阈值时不出正式信号。
3. `base_score = 0.35 * low_score + 0.65 * auction_score`（这里的权重为示例，需通过配置和回测验证；不再将“无风险”作为可凭空加分的15%）。
4. 软风险`risk_penalty`以0–100分扣减，并保存具体触发条件与证据；`total_score=clamp(base_score-risk_penalty, 0, 100)`。
5. 排名稳定器：相同分数按数据质量、明确的次级指标、代码确定性排序；不以缺失字段填0制造随机波动。

```python
def weighted_auction_score(values, weights, *, min_coverage=0.70):
    valid = {key: v for key, v in values.items() if v is not None and key in weights}
    coverage = sum(weights[k] for k in valid) / sum(weights.values())
    if coverage < min_coverage:
        return None, coverage
    score = sum(valid[k] * weights[k] for k in valid) / sum(weights[k] for k in valid)
    return round(max(0, min(100, score)), 2), coverage
```

### 5.4 诱多/高开风险的阶段修订

- **09:15–09:20**：在有充分原始申报/未匹配量证据情况下记录“疑似撤回影响”；没有申报级数据时不能据此断言撤单。
- **09:20–09:25**：只评估虚拟价变动、匹配量、未匹配量走势、稳定性，不将它写为撤单行为。
- 高开风险依据板块和证券限制动态判定；如源无法确认涨跌停制度就只标风险，不使用统一>9%的硬规则。
- 昨日炸板/连板标签保持原稿复用逻辑，但应区分策略排除条件与概率性的软风险。

### 5.5 信号结果语义

每只股票输出：`low_score`、`auction_score`、`total_score`、`factor_coverage`、`quality`、`confirmed_fields`、`events`、`risk_flags`、`excluded_reason`、`strategy_version`；只展示能追溯的预测/最终竞价价格及量。不得文案直接表示“机构正在买入”“主力建仓”，除非存在可验证的对应级别数据。

## 6. 数据库、快照与跨进程一致性

### 6.1 SQLite表（原3表扩为5表）

在原稿`AuctionFrame / AuctionCandidate / AuctionPerf`基础上新增`AuctionRun / AuctionOutbox`，并按下表修改原表字段/索引。所有新增/改动集中在`plugin_models.py`；项目若已有迁移工具必须通过迁移实施。**`Base.metadata.create_all()`只能建缺失表，不能自动修改已存在表的列或约束**。

| 表 | 关键字段（除自增ID） | 唯一/查询索引 |
|---|---|---|
| `auction_runs` | `trade_date,strategy_version,phase,state,revision,pool_hash,started_at,confirmed_at,published_at,last_error` | UNIQUE(`trade_date,strategy_version,phase,revision`)，(`trade_date`,`state`) |
| `auction_frames` | `frame_uid,trade_date,code,source,source_timestamp,received_at,indicative_price_yuan,indicative_match_shares,unmatched_shares,raw_volume_unit,quality,raw_payload_hash,raw_json` | UNIQUE(`frame_uid`)，INDEX(`trade_date`,`code`,`received_at`) |
| `auction_candidates` | `trade_date,code,strategy_version,phase,revision,low_score,auction_score,total_score,quality,coverage,source,source_timestamp,excluded_reason,confirmed_fields_json,rank` | UNIQUE(`trade_date,code,strategy_version,phase,revision`)，INDEX(`trade_date`,`rank`) |

约束：

- 所有数据库/JSON日期含交易日；时间戳统一包含`+08:00`，内部避免裸`datetime.now()`。
- 竞价帧保持内存滑动窗口，后台可批量落关键帧；**9:25关键路径只持久化最小`run+candidates+outbox`元数据**，不进行全部帧长事务。
- 推荐SQLite WAL、`busy_timeout`、短事务、UPSERT和唯一键；在多进程情况下测试并发写入锁。
- 非TopN也保存至少最终评分、数据质量、过滤原因及关键时间点摘要，避免复盘产生幸存者偏差；全量高频帧可按存储预算留样。

### 6.2 原子发布与Outbox事务顺序（必须实现）

避免“查询已经看到榜单但推送任务未入库”和“邮件先发但查询还是旧榜单”两种不一致：

```text
(1) 计算不可变的final_payload，生成snapshot_version + event_key
(2) 短DB事务：upsert auction_runs(state=PENDING_PUBLISH)
                 + auction_candidates + auction_outbox(status=WAITING_PUBLISH)
(3) 提交成功后：JSON写临时文件 → fsync(按环境需求) → 同卷atomic rename
(4) 短DB事务：runs(state=PUBLISHED,published_at=...)
                 + outbox(status=READY)
(5) worker只消费READY；读取接口只返回已发布版本
```

**崩溃恢复**：启动时扫描`PENDING_PUBLISH`与`WAITING_PUBLISH`，核对快照版本；存在一致有效payload则完成发布，不一致则重建快照或明确失败，不能悄然丢任务。若(4)异常，恢复程序负责补标`READY`。原快照双写`reports/`与`data_backend/`如无法做到两个位置同时原子化，应以`run/snapshot_version`为一致性判据，读优先使用最新**完整**版本。

### 6.3 快照契约（前端主读路径）

```json
{
  "status": "completed",
  "phase": "CONFIRMED",
  "trade_date": "<YYYY-MM-DD>",

  "snapshot_version": "<unique-version>",
  "pool_asof_date": "<previous-trading-date>",
  "pool_count": 0,
```

`items`中每票需带`source/source_timestamp/received_at/quality/factor_coverage/phase`以及价格/量的明确单位；无数据时返回空数组及正确状态，不放入虚构示例行情。

### 6.4 同机多进程读取

- `AuctionStore`只供采集进程维护，API进程默认读原子快照与SQLite。
- 如果前端要实时观察09:15–09:25的预测榜单，可每轮节流发布独立`auction_radar_preliminary.json`，或通过小规模数据库状态桥接；不得假定API可直接访问daemon内存。
- SSE必须考虑跨进程更新：通过`snapshot_version`变化检测广播，纯进程内`publish_snapshot_update`不自动跨进程生效。

## 8. 推送链路：邮件与Webhook快实时且可恢复

### 8.1 消息类型与时机

| 类别 | 触发 | 标题/内容原则 |
|---|---|---|
| 正式竞价榜单 | 确认完成且快照已发布 | `【低位竞价雷达】09:25最终确认 Top N`；数据时间、质量、免责说明 |
| 未确认告警 | 等待最终行情到期 | `【竞价数据未确认】今日不发送正式榜单`；清楚列出原因 |
| 系统采集故障 | 连续异常并达到阈值 | `【竞价雷达故障】`；不能包含伪造标的 |
| 更正版本 | 已发正式榜单后有受验证更正 | 显示revision/旧新差异；按策略是否额外推送 |

### 8.2 独立Outbox Worker

- 一个逻辑事件按`(trade_date,phase,strategy_version,revision)`生成稳定`event_key`；每通道和收件人生成独立Outbox记录。
- 状态：`WAITING_PUBLISH→READY→SENDING→ACCEPTED`；失败`RETRY_WAIT→READY`或`FAILED_FINAL`；`ACCEPTED`表示远端服务**接收请求**，不是投递到用户设备。
- Worker领取任务要使用租约字段`lease_until`，崩溃后自动回收；最大次数、指数退避+抖动、超时原因、下一次尝试时间单独存储。
- 远端超时但实际上已接受时无法保证绝对“恰好一次”；本地唯一键只防止本地重复入队，外部去重尽可能使用平台支持的业务消息ID或标记。
- 4个Webhook与邮件**各自独立执行**；不能让第一个渠道超时拖慢其他渠道。

### 8.3 邮件细则

- 检查原`send_email`是否同步阻塞；若是，在`asyncio.to_thread(...)`或独立线程Worker执行，禁止阻塞采集事件循环。
- 09:10完成DNS/端口/认证能力健康检查（不得为检查向用户误发测试消息）；连接可选预热并在使用前校验，断连时重连；保留TLS与身份验证。
- HTML模板盘前预编译，9:25只填数；邮件应展示`asof`、确认状态、来源、因子覆盖度、风险说明。
- 严格区分`SMTP_ACCEPTED`和`INBOX_DELIVERED`，后者需要独立收件箱探针或人工采样测量，不能由发送函数直接推断。
- `send_email`如无返回可观测的投递受理信息，包装适配器并记录异常；失败重试不得无限发送。

### 8.4 Webhook细则

- 使用平台标准鉴权与签名；Webhook地址、Token只在环境变量中，日志脱敏。
- 保持异步HTTP客户端复用连接；每通道独立超时、错误码判断和可重试分类。
- 对机器人平台返回HTTP 200但业务JSON错误码非成功的情况判为失败。
- 每条即时消息只保留简洁TopN与完整报告链接/快照版本；邮件承载更完整表格。

## 9. 性能、监控、恢复

### 9.1 端到端时间点（必须落日志/指标）

```text
source_timestamp     源实际行情时间（可能为空）
received_at          本地成功接收时间
validated_at         数据校验完成时间
scored_at            评分完成时间
final_confirmed_at   最终竞价确认时间
published_at         最终榜单可查询时间
webhook_accepted_at  Webhook服务端受理时间
smtp_accepted_at     SMTP服务端受理时间
```

采用`time.monotonic()`记录单进程阶段耗时；绝对时间采用Asia/Shanghai时区。校准系统时钟；源时间不可信时不计算伪造的“源到本地延迟”。

### 9.2 建议的第一版目标（以真实交易日P95验收，不是服务保证）

| 指标 | P95目标 | 起止口径 |
|---|---|---|
| 增量评分 | ≤200ms | 有效行情收齐→评分完成 |
| 最终榜单发布 | ≤1s | 最终行情确认→快照可读 |
| 本地`GET /latest` | ≤200ms | HTTP请求→完整响应 |
| Webhook服务端接受 | ≤5s | 快照发布→服务端有效接受 |
| SMTP服务端接受 | ≤15s | 快照发布→SMTP服务端接受 |
| 09:25后的通知 | 尽力在09:25:15前完成**提交** | 前提：足够早获得并验证最终行情；统计未达标原因 |

对源供应商实际更新时间另设分布统计，不能将“源到达慢”误报成“内部程序计算慢”。实盘收件箱送达不受本系统独立控制，必须另测实际到达时间。

### 9.3 运行稳定性

- `launchd`保活，但**Mac睡眠时无法保证任务按时执行**；增加睡眠/唤醒与关键时间错过监控、主机时钟漂移检测。
- 启动时读取DB/快照恢复当日`auction_runs`和Outbox；09:25后启动若无法补到最终数据，不能回放旧预测当最终结果。
- 看门狗监控`heartbeat_age`,`valid_quote_coverage`,`source_error_rate`,`last_confirmed_age`,`outbox_backlog`,`notification_accept_latency`。
- 连续失败时发送**系统告警**，而非生成虚假证券交易信号；告警自身需冷却和渠道去重。
- 全源失败/无池/非交易日必须可解释地停止正式信号推送。

| 类别 | 场景 | 预期 |
|---|---|---|

| 一致性 | DB事务成功、快照原子替换前崩溃 | 重启重建并发布或标失败，不丢outbox |
| 一致性 | 快照替换成功、READY前崩溃 | 恢复后任务最终可执行 |
| 源 | HTTP200但行情是昨日 | `STALE/INVALID`，不进入正式榜单 |
| 源 | 主源失败、备用源缺未匹配量 | 仅可用字段参与评分，质量和源逐票标注 |

## 13. 开发完成判定（Definition of Done）

同时满足以下条件才可关闭施工任务：

1. 原稿已验证的缺陷全部有复现、修复和回归测试；未验证的判断没有写成已修复事实。
2. 行情源字段报告有真实交易日样本及可复核对照；所有因子数据单位和语义清晰。
3. 交易日09:15前自动准备、09:25后确认为真才发正式榜单；未确认不会被悄然当作已确认。
4. GET查询走纯本地快照/DB，无外部行情调用；单个查询失败不阻塞采集。
5. 邮件、Webhook的异步与Outbox完成故障注入；各通道状态独立，重复触发受业务键限制。
6. 日志能解释每次信号从行情到快照再到SMTP/Webhook的延迟；满足或如实记录未满足性能目标的原因。
7. 具备启动/停止、故障恢复、非交易日、睡眠错过时段的运维说明。
8. 不自动交易，不承诺收益；对被遗漏、延迟、失真的信号有清晰数据状态与风险提示。
