# 23 主力资金扫描重构 v2：可验证漏斗、单写者与同源日内特征

> 状态：施工方案，供后续开发实现。
>
> 本文取代 `23_主力资金扫描重构_单请求榜单与分钟历史.md` 作为最新施工依据；旧文档保留为审查历史，不再直接照单开发。
>
> 适用范围：`principal_capital` 主力资金扫描、其向 `smart_money_radar` 输出的观察池，以及对应 GitHub Actions 调度和状态持久化。

## 0. 结论和强制边界

v2 保留“新浪全市场 bulk 粗筛 → 新浪单股接口精算”的漏斗方向，但不把抽样无越界当成不漏证明。上线分两阶段：

1. **strict/shadow 阶段**：正式结果继续来自新浪全量逐票扫描；同一批全量结果同时作为真值，对 bulk 漏斗做零额外精算请求的影子比较。
2. **hybrid 阶段**：只有连续 5 个交易日达到本文验收门槛后，正式结果才切换为 bulk 候选并集 + 精算；关键时点继续执行全量哨兵扫描，发现一次漏检就自动回退 strict。

以下规则是实现红线：

- 不修改 `filter_buy_candidates`、`filter_sell_candidates` 的阈值、板块、ST、成交额过滤逻辑。
- bulk 行永远不能直接进入上述 filter，必须经过单股精算得到完整资金分类。
- 不允许用买 10 只、卖 20 只之类随机抽样证明“全市场不漏”。
- 正式环境只有一个扫描和状态写入者；本地任务不得与 GitHub Actions 同时发送邮件、更新去重或覆盖报告。
- 邮件去重状态、候选池状态和日内特征状态必须分开，不能继续用 `buy_triggered` 代表当前候选池。
- 不跨供应商做分钟差分；切源、跨日、累计值回退时必须开新段并进入 warming。
- 不把 `fetched_at` 冒充供应商 `source_time`。缺少源时间的数据必须显式标注质量限制。
- `partial`、`degraded`、`stale` 结果不得标成 `completed`，不得发送依赖完整覆盖的正式通知。

## 1. 当前基线和 v1 需要纠正的事实

### 1.1 当前实现

- `backend/plugins/principal_capital/service.py` 每轮调用 `fetch_market_fund_flow_resilient()`，再直接执行现有买卖过滤。
- `backend/plugins/principal_capital/sources/multi_source.py` 当前顺序仍为 Eastmoney → AKShare → Sina，Sina 路径是全主板逐票请求。
- `backend/plugins/principal_capital/sources/sina_market.py` 尚无 bulk 正式适配器。
- `principal_capital_latest.json` 仅保存本轮 fresh 触发项，没有当前全部候选和当日最新状态。
- `smart_money_radar.load_watch_pool()` 实际回退读取 `buy_triggered/sell_triggered`，因此买入日内去重会导致池子后续轮次丢失。
- GitHub Actions 已采用“上午/下午各一个长任务、任务内每 5 分钟循环”的方式，不再是 13:10 后断供。

### 1.2 v1 的错误假设

| v1 假设 | v2 结论 |
|---|---|
| `ratioamount` 40/-24 能保证不漏 `main_inflow_ratio` 50/-30 | 两字段资金分类不同，无数学包含关系，只能作为经验漏斗 |
| 圈定外抽样 10/20 只为零越界即可上线 | 证据不足；必须用同轮全量逐票真值比较 |
| 候选数少于 5 才放宽阈值可以覆盖极端行情 | 候选数多也可能漏检，不能作为漏检保险 |
| GitHub Actions 和本地 daemon 双跑幂等 | 邮件、去重、驻留、报告都有副作用，双写不幂等 |
| `_today` 合并 fresh 行即可得到最新状态 | 已触发过的股票后续不再 fresh，指标会永久停在首次值 |
| 东财分钟历史适合继续做主路径 | 当前部署出口已多次失败；只能作为独立可选增强 |
| 11:30/15:00 精确匹配即可发摘要 | 当前循环到边界先退出，必须使用 session finalizer 和幂等发送标记 |

## 2. 目标、非目标和优先级

### 2.1 目标

| 优先级 | 目标 | 验收口径 |
|---|---|---|
| P0 | 不让优化引入已知漏检 | strict/shadow 期间每轮用全量真值计算 false negative；放行窗口为零 |
| P0 | 单一正式写者 | 每个批次只有一个 `owner_id`，只有 official 模式能发信和写正式状态 |
| P0 | 失败状态真实 | 精算覆盖不足、源时间未知、缓存超龄均进入明确质量状态 |
| P1 | 降低常态请求量 | hybrid 暖态请求数相对全量逐票下降至少 70% |
| P1 | 雷达池连续 | 当前候选、首次出现、最后出现、驻留状态可以跨轮恢复 |
| P1 | 形成可解释的日内资金特征 | 只对同源、同交易日、连续累计快照做差分 |
| P2 | 尾盘和摘要可靠 | 14:30、14:40、14:50 有扫描；午间和收盘摘要恰好一次 |

### 2.2 非目标

- 不在本任务中改变买入 50%、卖出 -30% 等策略阈值。
- 不把 TDX 成交数据解释成供应商“主力资金”分类。
- 不承诺免费数据源拥有交易所级 source_time 或生产 SLA。
- 不新增 Redis、外部数据库或付费行情依赖。
- 不在 v2 首批删除 Eastmoney/AKShare 旧适配器；它们保留为兼容路径，但不能绕过质量门控。
- 不修改 `tier_flow`、隔夜套利或其它插件的业务公式。

## 3. 总体架构

```text
GitHub Actions official owner（每个交易时段一个长任务）
  |
  +-- RoundContext：batch_id / owner_id / trade_date / mode / deadline
  |
  +-- strict 模式
  |     新浪主板清单 -> 全量逐票精算 -> 现有 filter -> 正式结果
  |                              |
  |                              +-> 同轮 bulk 漏斗影子比较
  |
  +-- hybrid 模式
  |     新浪 bulk -> 候选并集 -> 逐票精算 -> 现有 filter -> 正式结果
  |                        +-> 圈定外确定性轮转审计
  |                        +-> 关键时点全量哨兵扫描
  |
  +-- 当前候选状态 -> 雷达观察池
  +-- 同源累计快照 -> 日内差分特征
  +-- session finalizer -> 午间/收盘摘要
  +-- 原子写状态和报告 -> data-snapshots

本地/manual：只允许 shadow 或 readonly，不发信、不写 official 状态
watchdog：只检查新鲜度和失败，不参与正式扫描
```

## 4. 执行模式和唯一写者

### 4.1 三种模式

| 模式 | 是否写正式报告 | 是否改去重/状态 | 是否发信 | 用途 |
|---|---:|---:|---:|---|
| `official` | 是 | 是 | 按规则 | GitHub Actions 唯一正式任务 |
| `shadow` | 只写 `*_shadow.json` | 写独立 shadow 状态 | 否 | 灰度对照、本地验证 |
| `readonly` | 否 | 否 | 否 | 手工诊断、接口检查 |

新增环境变量：

```text
PC_EXECUTION_MODE=official|shadow|readonly
PC_OFFICIAL_OWNER=github_actions
PC_PIPELINE_MODE=strict|hybrid
```

规则：

- GitHub workflow 显式设置 `PC_EXECUTION_MODE=official` 和 `PC_OFFICIAL_OWNER=github_actions`。
- 未设置 `PC_EXECUTION_MODE` 时默认 `readonly`，避免本机误发邮件。
- `smart_money_radar.scheduler` 不调用 `run_principal_capital_scan()`。
- `official` 模式启动时生成 `owner_id={github_run_id}:{job}:{session}`，写入每个报告和状态文件。
- 状态同时保存 `owner_lease_expires_at`；official 每轮开始续租 10 分钟，session finalizer 完成后主动释放。
- 状态中若已有同交易日、租约未过期且不同的 official owner，当前任务退出 `owner_conflict`，不发送邮件。上午租约释放或过期后，下午任务可以接管同一交易日状态。
- GitHub workflow 的 `concurrency` 继续禁止同一分支出现两个 official job。
- `dry_run` 只控制邮件不够安全；v2 必须以 execution mode 控制所有副作用。

### 4.2 调度决策

沿用现有 workflow 的上午/下午长任务和任务内 5 分钟循环，不改成 70 个独立 cron job。

- 上午循环：首次有效触发后运行到 11:30。
- 下午循环：首次有效触发后运行到 15:00。
- 每轮使用北京时间的 aware datetime。
- 每轮完成后立即提交紧凑状态和报告快照，确保任务中断后去重与池状态可恢复。
- 到达 session 边界后，workflow 必须额外调用一次 finalizer，然后再提交快照。
- `14:30/14:40/14:50` 通过“跨过目标时间且该时点未执行”语义保证，不要求系统恰好在整分钟启动。

需要新增 CLI：

```text
python -m backend.main --run-principal-capital-scan --execution-mode official
python -m backend.main --finalize-principal-capital-session --session am
python -m backend.main --finalize-principal-capital-session --session pm
```

RoundContext = {

### 5.5 v2 资金源路由

- strict 主路径固定为 `sina_full`：主板清单 + 新浪单股全量精算。这样 strict 真值与未来 hybrid 使用同一资金分类口径。
- 只有 `sina_full` 完整成功时，才执行新浪 bulk 的 shadow 集合对照。
- Sina 全量失败时，可以调用现有 resilient 路径取得已准入的备用源，但批次必须标 `pipeline_mode=strict_fallback`，不参与 bulk 准入统计，也不与新浪累计序列相减。
- Eastmoney 和 AKShare 属同一上游家族，共享失败预算；不能在同一轮通过多个包装连续轰炸相同上游。
- 缓存只允许页面展示和维持已有雷达成员，不产生新候选、日内差分或 direct 通知。
- 所有源均失败时输出 `no_data`；不得拿上一轮候选伪装成当前完整扫描。

## 6. Bulk 准入门槛

在 `PC_BULK_ADMITTED=1` 之前，bulk 只能在 shadow 中运行。准入脚本必须确定性检查整份响应：

1. 响应是列表且 schema_version 匹配。
2. 代码可唯一标准化，沪深身份不冲突。
3. 与当日有效主板清单比较，记录分母、缺失代码和额外代码；覆盖率必须 100%，停牌等例外要有原因映射。
4. 所有关键数值为有限数，缺失与合法零值分开。
5. `amount`、`ratioamount`、`r0_ratio` 的单位通过固定夹具和单股端点交叉验证，不按数值大小猜单位。
6. 记录完整请求 URL 标识、fetched_at、响应行数、延迟和内容摘要 hash。
7. 交易时段连续 5 个交易日，每日至少覆盖开盘、午前、午后、尾盘四个窗口。

准入失败时：

- strict 正式扫描不受影响。
- shadow 报告写明 `bulk_admitted=false` 和失败原因。
- 禁止因为 HTTP 200 或行数大于 5000 自动转为 hybrid。

## 7. 候选漏斗与“不漏”验证

### 7.1 候选并集

hybrid 粗筛不是单阈值，而是以下集合的并集：

```text
coarse_codes =
    ratioamount 正向候选
  ∪ ratioamount 负向候选
  ∪ r0_ratio 正负极值候选
  ∪ r0_net 正负金额极值候选
  ∪ 上一轮 current candidates
  ∪ 当日仍在 min_dwell 的雷达池代码
  ∪ complement audit 本轮分片
```

初始经验参数仍可使用买 40、卖 -24，但必须标成“经验参数”，不能叫安全边界。`r0_ratio`、`r0_net` 的初始阈值和头部数量由 shadow 数据分布产生，不在代码中凭空硬编码。

### 7.2 strict/shadow 的零额外请求比较

strict 模式已经取得全量逐票结果，因此 shadow 比较不再对候选重复请求：

```python
truth_buy = filter_buy_candidates(full_refined_df)
truth_sell = filter_sell_candidates(full_refined_df)

shadow_df = full_refined_df[code in coarse_codes]
shadow_buy = filter_buy_candidates(shadow_df)
shadow_sell = filter_sell_candidates(shadow_df)

false_negative_buy = truth_buy - shadow_buy
false_negative_sell = truth_sell - shadow_sell
```

每轮保存 false positive/negative 代码、它们对应的 bulk 字段以及漏检原因。这里比较的是同一批逐票真值，禁止用不同分钟抓取的数据做集合 diff。

### 7.3 hybrid 运行后的持续审计

hybrid 正式运行后仍保留两层审计：

- **轮转补集审计**：对粗筛外代码按稳定 hash 分片，不随机抽样；使用 `SHA-256(code) % bucket_count`，禁止使用进程间不稳定的 Python `hash()`；每轮精算一片，确保所有补集在配置窗口内被覆盖。
- **全量哨兵扫描**：默认在 09:35、10:30、13:30、14:30、14:50 执行全量新浪逐票扫描，并与该轮 hybrid 集合比较。

自动回退条件，任一满足即生效：

- 哨兵轮出现 1 个买侧或卖侧 false negative。
- bulk 覆盖率低于 100%，且缺失代码没有已知非交易原因。
- coarse 或精算阶段关键字段 schema 变化。
- 候选精算最终覆盖率低于 100%。
- 连续两轮总耗时超过 deadline。

回退动作：

1. 当前轮状态标记 `partial`，不发送依赖完整性的 direct 通知。
2. `PC_PIPELINE_MODE` 的运行状态切为 `strict_auto_fallback`，当天余下轮次全量扫描。
3. 写入 `fallback_reason` 和触发代码。
4. 后续连续 5 个完整交易日 shadow 零漏检后才允许重新 hybrid，不能自动在几轮后恢复。

## 8. 精算阶段

### 8.1 请求预算

- 默认并发 `PC_REFINE_WORKERS=20`，但同时增加令牌桶，初始 `PC_REFINE_QPS=20`。
- 单请求连接/读取 timeout 默认 8 秒。
- 每轮总 deadline 默认 90 秒；请求提交前检查剩余预算。
- 失败代码只重试一次，重试并发降到 5，并加入 100–300ms 抖动。
- 不允许 executor 退出时无限等待；必须有底层 timeout 和有界待提交队列。

### 8.2 失败语义

```text
全部候选成功                     -> refine_status=complete
有失败，重试后全部恢复           -> refine_status=recovered
仍有任一候选失败                 -> batch status=partial
批次 deadline 用尽               -> batch status=deadline_exceeded
```

失败代码不能以零资金或非候选处理。`partial` 批次允许：

- 展示已取得的数据，并明确显示覆盖范围。
- 保留上一轮雷达池成员到其最大陈旧期限。

`partial` 批次禁止：

- 声称全市场扫描完成。
- 根据缺失集合为空的假设发送正式卖出邮件。
- 把失败代码从当日累计和驻留状态中删除。

## 9. 日内状态模型

新增 `backend/plugins/principal_capital/intraday_state.py`，状态落到：

```text
data/principal_capital_intraday_state.json
```

使用唯一临时文件 + `os.replace()` 原子写。文件按交易日重置，最多保留当前交易日必要序列。

### 9.1 顶层结构

```json
{
  "schema_version": 2,
  "trade_date": "2026-09-15",
  "owner_id": "...",
  "owner_lease_expires_at": "...",
  "last_batch_id": "...",
  "pipeline_mode": "strict",
  "auto_fallback": null,
  "summary_sent": {"am": false, "pm": false},
  "audit_cursor": 0,
  "candidates": {},
  "pool_entries": {},
  "fund_series": {}
}
```

### 9.2 candidates

按 `direction:code` 保存：

```json
{
  "buy:600000": {
    "first_seen_at": "...",
    "last_seen_at": "...",
    "last_batch_id": "...",
    "seen_rounds": 4,
    "is_current": true,
    "latest_metrics": {},
    "quality_status": "provisional"
  }
}
```

每个完整批次：

- 本轮所有候选更新 `latest_metrics` 和 `last_seen_at`。
- 首次出现的键 `fresh=true`；已存在的键 `fresh=false`。
- 上一轮存在、本轮完整扫描未命中的键设 `is_current=false`，但保留当日历史。
- partial 批次不得据此把未命中键设为 false。
- `buy_triggered`/`sell_triggered` 继续作为兼容字段，含义保持“本轮满足通知去重条件的 fresh 行”。
- 新增 `buy_candidates_current`/`sell_candidates_current` 保存本轮全部候选行。
- 新增 `buy_candidates_today`/`sell_candidates_today` 保存当日出现过的最新行。

### 9.3 邮件去重

继续使用既有 notified 文件和冷却语义，但仅由 notification 模块读写。候选状态更新不读取 notified 文件，保证“是否发过邮件”不会改变雷达池数据。

## 10. 同源日内资金特征

### 10.1 默认主路径

v2 默认使用每轮新浪单股精算得到的累计资金值形成快照差分，不再把东财分钟接口作为主路径。

每个 code 最多保留最近 24 个观测：

```json
{
  "observed_at": "2026-09-15T14:35:02+08:00",
  "source_segment": "sina_single:v1:2026-09-15",
  "main_net_inflow": 12345678.0,
  "total_amount": 98765432.0,
  "batch_id": "..."
}
```

只有同时满足以下条件才计算相邻差分：

- 同一证券、同一交易日、同一 `source_segment`。
- 两次观测间隔 2–10 分钟。
- 当前 `total_amount >= previous.total_amount`。
- 数值均为有限数。
- 两个批次均不是 stale、partial 或 cache。

否则开新段并输出 `warming=true`，记录原因：`first_observation`、`source_changed`、`gap_too_large`、`counter_reset`、`batch_partial` 等。

### 10.2 特征定义

```python
delta_main_net = current.main_net_inflow - previous.main_net_inflow
delta_total_amount = current.total_amount - previous.total_amount
inc_ratio = delta_main_net / delta_total_amount * 100  # 分母 > 0
```

- `roll_net_30m`：按时间范围累加最近 30 分钟有效 `delta_main_net`，不是简单取最后 6 行。
- `acc_win`：从最新值向前数连续 `delta_main_net > 0` 的有效窗口数。
- `inc_ratio_5m`：最新有效差分的 `inc_ratio`；实际间隔同时写入 `interval_seconds`。
- 最近 30 分钟有效覆盖不足 25 分钟，或最大间隙超过 10 分钟时，`roll_net_30m=None`、`warming=true`。
- 午休前后的两个观测不能组成一个 5 分钟窗口。

### 10.3 东财分钟接口的定位

Eastmoney fflow 只允许输出独立命名空间：

```text
experimental_features.eastmoney_fflow.*
```

它不能覆盖新浪差分特征，不能与新浪累计值拼接，不能因为恢复一次就自动晋升。只有独立完成可达性、源时间、字段语义和连续 5 日验证后，才能通过单独变更提升能力等级。

## 11. 雷达池策略

雷达池只消费 `buy_candidates_current` 和处于保留期的历史买侧成员；卖侧候选不混入同一个吸筹观察池。

默认参数：

```text
RADAR_POOL_MAX=40
RADAR_POOL_MIN_DWELL_MIN=30
RADAR_POOL_PROTECTED_CAP=30
RADAR_POOL_ROTATION_SEATS=10
RADAR_POOL_MAX_STALE_MIN=15
```

选择顺序：

1. 读取本轮完整的 `buy_candidates_current`。
2. 保留进入池未满 30 分钟且未超过最大陈旧时间的成员，按当前分数最多保留 30 席。
3. 剩余席位优先放本轮 fresh 候选，再按 `main_inflow_ratio`、`main_net_inflow`、`last_seen_at`、code 做稳定排序。
4. 至少保留 10 个轮换席，防止 40 个旧成员把新候选完全堵死。
5. partial 批次不主动驱逐旧成员，只更新成功取得的成员；超过 `RADAR_POOL_MAX_STALE_MIN` 后才移除。
6. 每个成员写 `entered_at`、`last_seen_at`、`dwell_until`、`selection_reason` 和 `source_batch_id`。

池状态并入 `principal_capital_intraday_state.json`，不再另建容易产生批次不一致的 dwell 文件。

## 13. 午间和收盘摘要

新增 `finalize_principal_capital_session(session, now, execution_mode)`：

- `session=am` 汇总截至上午收盘的 `buy_candidates_today`。
- `session=pm` 汇总全天 `buy_candidates_today`。
- 使用状态中的 `summary_attempted`、`summary_sent` 保证正常执行下至多发送一次。
- official + notify_eligible 才发送；shadow/readonly 只构造内容用于测试。
- finalizer 不重新抓行情，不修改候选值，只读取最近一个完整批次。
- 最近完整批次超过 15 分钟时不发送，写 `summary_skipped_reason=latest_batch_stale`。
- 标题固定带“日内汇总”，不得与实时卖出参考共用标题模板。
- SMTP 不支持业务幂等键，进程可能在邮件服务已接收后、状态落盘前崩溃，因此不能承诺分布式意义上的 exactly-once。
- 发送前先原子写 `summary_attempted_at`；发生结果不明的中断时不自动重发，由 watchdog 标记 `delivery_unknown`。只有传输明确失败时才允许手工重试；成功后写 `summary_sent_at`。

## 17. 必须覆盖的测试

### 17.1 Bulk 和单位

- 正常整表、空列表、非列表、缺列、重复代码、错误市场前缀。
- `ratioamount` 原始比例与百分数夹具，验证只转换一次。
- NaN/Infinity/`-`/空字符串不得变成合法零。
- 实际主板分母 100%、缺 1 只、额外指数/基金、停牌有原因四种覆盖场景。
- source_time 缺失时只能 `coarse_candidate`，不能 `notify_eligible`。

### 17.2 漏斗与真值

- 构造 `ratioamount` 低但 `main_inflow_ratio >= 50` 的买侧反例，必须被 shadow 标成 false negative。
- 构造 `ratioamount` 高但 `main_inflow_ratio <= -30` 的卖侧反例。
- 多条件并集去重且顺序稳定。
- 上轮候选、驻留成员和 audit 分片都能进入精算集合。
- 同轮 truth/hybrid diff，禁止比较不同 batch_id。
- 哨兵发现一个漏检后状态立即变 `strict_auto_fallback`。

### 17.3 精算失败

- 首次失败、重试恢复。
- 重试后仍缺 1 只，批次必须 partial。
- deadline 前不再提交新请求。
- partial 批次不发送邮件、不驱逐未知成员、不把 scanned 写成 requested。
- executor 中慢请求受底层 timeout 约束。

### 17.4 日内状态

- 首次候选 fresh=true；第二轮指标更新且 fresh=false。
- 完整批次未命中后 is_current=false。
- partial 批次不把旧候选误标离场。
- 跨交易日清空日内候选、序列、摘要标记和 audit cursor。
- 同 batch 重放幂等，不重复增加 seen_rounds，不重复发送摘要。
- 不同 official owner 冲突时拒绝写入。
- 原子写中断后旧文件仍可读取。

### 17.5 分钟特征

- 同源连续 5 分钟快照正确差分。
- 切源、跨日、午休跨越、间隔超过 10 分钟、累计成交额回退均 warming。
- 30 分钟按时间范围而不是固定 6 行。
- 覆盖不足 25 分钟时不得给 `roll_net_30m`。
- partial/cache/stale 观测不能参与连续窗口。

### 17.6 雷达池和摘要

- 30 个保护席 + 10 个轮换席，不被 40 个旧成员锁死。
- 新 fresh 候选按稳定顺序进入。
- partial 批次保留旧成员，超过最大陈旧期限后移除。
- 卖侧候选不进入吸筹观察池。
- 11:30/15:00 到达边界后 finalizer 正常路径各至多发送一次；明确失败允许手工重试，结果不明不得自动重发。
- 最近完整批次过期时摘要跳过且记录原因。

只有同时满足以下条件，才能把方案 23 v2 标记为“开发完成”：

1. M1–M4 代码和测试全部合入。
2. strict 模式行为与现有核心 filter 回归一致。
3. 本地默认 readonly，GitHub Actions 是唯一 official owner。
4. current/today/fresh 状态在完整、partial、跨日和重启场景均正确。
5. Bulk 仍处于 shadow，除非准入和连续 5 日门槛真实完成。
6. 未取得 5 日证据时，文档和报告只能写“代码完成、运行验收待完成”，不能写“方案全部完成”。
7. Hybrid 上线后保留哨兵扫描和自动 strict 回退，不能为了请求量指标移除正确性保险。

开发过程中如发现现有接口或字段与本文假设不一致，应先补充失败夹具和实测证据，再修改方案；不得静默改变字段单位、候选语义或通知条件。
